# 実装計画

- [ ] 1. サーバーとデータベースの土台を作る
- [x] 1.1 Go の API サーバーの雛形を作る
  - Go のプロジェクトを初期化し、サーバーの起動・マイグレーション・初期データ投入を1つのバイナリのサブコマンドとして実行できるようにする
  - 環境変数から設定（データベースの接続先、Firebase の認証情報、許可するオリジンなど）を読み込む仕組みを作る
  - 構造化ログ（リクエスト ID つき）と、死活監視用のエンドポイントを用意する
  - ローカルで PostgreSQL と Firebase Auth Emulator を起動できる開発環境を用意する
  - _Requirements: 20.1, 20.8（の前提となる実行基盤）_

- [x] 1.2 API 定義を先に書き、サーバーとクライアントの型を生成できるようにする
  - OpenAPI の定義ファイルを作り、共通のエラー形式（コード・メッセージ・入力欄ごとのエラー）と、日付・日時の表現を決める
  - 定義からサーバーのハンドラーの型と、モバイルアプリ用の型を生成する手順を整える
  - 項目を追加しても古いクライアントが壊れないこと（知らない項目・列挙値を無視すること）をルールとして定義に反映する
  - ドメインのエラーを、HTTP のステータスとエラーコードに一か所で変換する仕組みを作る
  - _Requirements: 19.9, 1.3, 4.3, 4.4_

- [ ] 1.3 データベースのスキーマを作る
  - ユーザー・端末・世帯・メンバーシップ・招待・植物マスタ・置き場所・植物・お手入れタスク・お手入れ記録・メモ・提案・通知のアウトボックス・リマインダーの送信記録のテーブルを、マイグレーションとして作る
  - 同じ予定の回への完了を1件に限る部分ユニーク制約、招待トークンと招待コードのユニーク制約、リマインダーの1日1回のユニーク制約、提案の重複防止のユニーク制約を入れる
  - 世帯・植物の削除時のカスケード、置き場所の削除時に植物の置き場所を未設定にするルール、タスクの論理削除を反映する
  - 将来の項目を入れられる拡張用の列を、世帯・置き場所・植物・植物マスタに持たせる
  - SQL から型安全なアクセスコードを生成する仕組みを整え、テスト用の PostgreSQL コンテナで結合テストを回せるようにする
  - _Requirements: 5.3, 11.4, 15.2, 17.6, 19.8, 2.6, 5.7, 7.4, 8.10_

- [ ] 2. 認証とアカウントの基本を作る
- [ ] 2.1 Firebase の ID トークンによる認証を API に組み込む
  - すべての API で ID トークンを検証し、トークンがない・無効・期限切れのリクエストを認証エラーで拒否する
  - 初めてアクセスしたユーザーの行を作り、認証プロバイダから受け取った名前を表示名の初期値にする
  - 自分のプロフィールの取得と、表示名の変更を提供する
  - 認証の成功・失敗のパターンを、エミュレーターを使ったテストで確認する
  - _Requirements: 1.2, 1.3, 20.2_

- [ ] 2.2 プッシュ通知の送信先となる端末の登録と解除を作る
  - 端末の通知トークン・OS の種類・端末のタイムゾーンを登録・更新できるようにする
  - サインアウト時に、その端末を通知の送信先から外せるようにする
  - 同じ通知トークンが別のユーザーで登録された場合は、新しいユーザーに付け替える
  - _Requirements: 1.5, 15.7_

- [ ] 3. 次回予定の計算と季節のルールを作る（ドメインの中心のロジック）
- [ ] 3.1 周期と季節から次回予定を計算するロジックを作る
  - 日・週・月の周期での次回予定の計算と、月末の丸め（1/31 の1か月後など）を実装する
  - 日付と半球から季節（春・夏・秋・冬）を判定し、季節ごとの周期があればそれを優先する
  - 完了した日を起点に、その日の季節で有効な周期を使って次回予定を決める
  - うるう年や季節の境目を含む境界値を、単体テストで網羅する
  - _Requirements: 8.1, 8.6, 10.2, 10.3, 10.5_

- [ ] 3.2 植え替えの適期の判定ロジックを作る
  - 購入日からの慣らし期間（14日）を過ぎた日以降で、最初に適期（4〜6月、9月）に入る日を求める
  - 真夏（7〜8月）・真冬（12〜2月）を、植え替えを避ける時期として判定できるようにする
  - 提案日を選んだ理由（慣らし期間のあと、避ける時期を飛ばした、など）を組み立てられるようにする
  - 月の境目（6/30、7/1、8/31、9/1、11/30、3/1 など）を単体テストで確認する
  - _Requirements: 17.2, 17.3, 17.7, 17.8_

- [ ] 4. 世帯・メンバー・権限を作る
- [ ] 4.1 ロールにもとづく権限の判定を作る
  - オーナー・編集者・閲覧者ごとに許可する操作を、ポリシー表として定義する
  - 世帯のメンバーでない場合は存在を明かさずに「見つからない」を返し、ロールが足りない場合は「権限がない」を返す
  - メモの編集・削除は、作成者本人かオーナーに限る
  - ロールと操作のすべての組み合わせを、単体テストで確認する
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 13.3, 20.2_

- [ ] 4.2 世帯の作成・一覧・変更・削除を作る
  - 世帯を作成し、作成したユーザーをオーナーにする
  - ユーザーが所属するすべての世帯を、それぞれのロールとともに一覧で返す
  - オーナーだけが、世帯名と地域（都道府県・市区町村）を変更できるようにする
  - オーナーだけが世帯を削除でき、配下のデータもすべて削除されるようにする
  - _Requirements: 2.1, 2.3, 2.5, 2.6, 7.5_

- [ ] 4.3 メンバーの管理・退出・オーナー権限の移譲を作る
  - メンバーの一覧、オーナーによるロールの変更、メンバーの削除を提供する
  - オーナー以外のメンバーが退出できるようにし、唯一のオーナーはほかのメンバーがいる限り退出できないようにする
  - オーナー権限を別のメンバーに移すと、元のオーナーが編集者になるようにする
  - 削除・退出したメンバーの過去の記録には、作業者名を残す
  - メンバーごと・世帯ごとの通知設定（リマインダーの有効・時刻、完了通知の有無）を、本人が変更できるようにする
  - _Requirements: 2.7, 2.8, 4.6, 4.7, 4.8, 12.5, 15.3, 16.3_

- [ ] 5. 招待と参加を作る
- [ ] 5.1 招待の発行・取り消しを作る
  - オーナーが、編集者または閲覧者のロールを指定して、有効期限つき（初期値7日）の招待を作れるようにする
  - 推測されにくいトークン（保存するのはハッシュのみ）と、紛らわしい文字を除いた8文字の招待コードを発行する
  - 招待リンクの URL を返し、オーナーが招待を一覧・取り消しできるようにする
  - _Requirements: 3.1, 3.7, 20.3_

- [ ] 5.2 招待の確認と参加を作る
  - 招待のトークンまたはコードから、世帯名と付与されるロールを返す
  - 参加を確定すると、指定のロールで世帯に追加する
  - 期限切れ・取り消し済みの招待を拒否し、すでにメンバーの場合は重複して追加しない
  - 招待の確認と参加に、利用者ごとのレート制限をかける
  - 参加があったことを、通知のアウトボックスに積んでオーナーに知らせられるようにする
  - _Requirements: 3.3, 3.5, 3.6, 3.8, 20.3_

- [ ] 6. 植物マスタ・置き場所・植物を作る
- [ ] 6.1 植物マスタと初期データを作る
  - 和名・学名・別名、光の量、耐寒性、湿度、風通し、水やりの傾向、屋外に出せるか、推奨周期・推奨の実行条件を持つ植物マスタを作る
  - 主要な室内観葉植物30〜50種の初期データを、出典つきで投入できるようにする
  - 和名・学名・別名のあいまい検索を提供する
  - 植物マスタは世帯とは別の、全ユーザー共通のデータとして扱う
  - _Requirements: 6.1, 6.2, 6.5, 6.6_

- [ ] 6.2 置き場所の登録・変更・削除を作る
  - 置き場所の名前と環境情報（室内か屋外か、窓の向き、窓からの距離、遮光の有無）を登録・変更できるようにする
  - 置き場所を削除すると、紐づく植物の置き場所が未設定になるようにし、削除前に紐づく植物の数を返せるようにする
  - 編集者以上だけが操作できるようにする
  - _Requirements: 7.1, 7.2, 7.3, 7.4_

- [ ] 6.3 植物の登録・一覧・編集・削除・アーカイブを作る
  - 名前（必須）、種類（植物マスタの選択または自由入力）、置き場所、購入日・お迎え日で植物を登録・編集できるようにする
  - 株数に上限を設けない
  - 一覧で、置き場所による絞り込みと名前での検索ができ、次のお手入れ予定日も返す
  - 植物の削除で、タスク・記録・メモも削除されるようにする
  - アーカイブした植物を、通常の一覧とリマインダーの対象から外し、記録とメモは閲覧できるようにする
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 5.7, 5.8, 6.3_

- [ ] 7. お手入れタスクを作る
- [ ] 7.1 お手入れタスクの作成・変更・削除を作る
  - 種類（水やり・肥料・植え替え・剪定・その他）、周期、初回の予定日、メモ、実行条件、季節ごとの周期を持つタスクを作れるようにする
  - 種類が「その他」の場合は作業名を必須にする
  - 植物がマスタと紐づいている場合、推奨周期と推奨の実行条件を初期値として返す
  - 周期・実行条件・予定日を変更できるようにし、予定日を手動で変えた場合は、季節の切り替えによる計算し直しの対象から外す
  - タスクを削除しても、過去の記録は履歴として残るようにする
  - _Requirements: 8.1, 8.2, 8.3, 8.4, 8.5, 8.6, 8.8, 8.10, 6.4_

- [ ] 7.2 タスクの一時停止と再開を作る
  - 一時停止したタスクを、予定・今日やること・リマインダーの対象から外す
  - 再開したときは、再開した日以降で次回予定を計算し直す
  - _Requirements: 8.9_

- [ ] 8. お手入れの記録（完了・スキップ・取り消し）を作る
- [ ] 8.1 完了の記録と、重複の防止を作る
  - 完了を記録すると、実施日・作業の種類・作業した人を保存し、次回予定を計算して予定の回の番号を進める
  - 過去の日付を実施日として記録できるようにし、予定日より前の完了も受け付ける
  - 同じ予定の回がすでに完了している場合は記録せず、誰がいつ完了したかと最新のタスクの状態を返す
  - 重複を承知で追加として記録する指定を受け付ける
  - 同じタスクへの同時の完了リクエストのうち、1件だけが成功することを並行実行の結合テストで確認する
  - _Requirements: 10.1, 10.2, 10.3, 10.5, 11.2, 11.3, 11.4_

- [ ] 8.2 スキップの記録を作る
  - スキップを記録すると、作業をしたことにはせず、理由（土がまだ湿っている・天気が悪い・株が弱っている・その他の自由入力）を保存する
  - タスクは未完了のまま、次回の確認日（初期値は翌日、変更できる）を予定日にする
  - スキップの理由を、将来の助言の改善に使える形で保存する
  - _Requirements: 10.6, 10.7, 10.8, 19.7_

- [ ] 8.3 取り消しと、まとめて完了を作る
  - 記録した本人が直後（10分以内）に取り消すと、記録前の予定日と予定の回に戻す
  - 最新の記録でないもの、時間が過ぎたものの取り消しを拒否する
  - 複数のタスクをまとめて完了でき、タスクごとに結果（成功・重複・エラー）を返す
  - _Requirements: 10.4, 10.9_

- [ ] 8.4 記録の編集・削除と、履歴の取得を作る
  - 編集者以上が、過去の記録の実施日を編集・削除できるようにし、最新の完了分であれば次回予定を計算し直す
  - 植物ごとの履歴を、新しい順に、作業の種類・完了かスキップか・理由・作業した人とともに返し、種類での絞り込みとページ送りに対応する
  - 作業の種類ごとの最終実施日を返す
  - _Requirements: 12.1, 12.2, 12.3, 12.4, 12.5_

- [ ] 9. 今日やること・メモ・カレンダーを作る
- [ ] 9.1 今日やること一覧を作る
  - アプリから渡された端末での今日の日付で、予定日が今日以前の未完了タスク（有効なもの、アーカイブされていない植物のもの）を返す
  - 各項目に、植物名・置き場所・作業の種類・予定日・実行条件・期限切れの日数を含める
  - 対象のタスクに有効な「やらない方がよい」「条件つき」の提案があれば、一緒に返す
  - 今日の作業がない場合は、直近の次の予定を返す
  - _Requirements: 9.1, 9.2, 9.3, 9.4, 9.6_

- [ ] 9.2 植物ごとのメモを作る
  - 編集者以上がメモを作成でき、作成日時と作成者を保存する
  - メモの一覧を新しい順に返す
  - 作成者本人かオーナーが編集・削除でき、編集済みであることがわかるようにする
  - 空のメモと、上限（2000文字）を超えるメモを拒否する
  - _Requirements: 13.1, 13.2, 13.3, 13.4, 13.5_

- [ ] 9.3 植物ごとのカレンダーのデータを作る
  - 指定した月について、その植物の記録（完了・スキップ）、今後の予定日、メモを書いた日を返す
  - 今後の予定は、現在の予定日と周期から、その月の範囲で展開する
  - _Requirements: 14.1, 14.3, 14.4, 14.5_

- [ ] 10. 助言プロバイダの仕組みと、植え替えの提案を作る
- [ ] 10.1 助言プロバイダの共通の仕組みを作る
  - 植物・植物マスタ・置き場所・世帯の地域・日付・過去の記録を受け取って提案を返す、プロバイダの共通の取り決めと登録の仕組みを作る
  - 提案の種類（実施をすすめる・やらない方がよい・条件つき）、対象、本文、理由、有効期間、提案元を保存する
  - 同じ提案（重複防止のキーが同じもの）を二度作らない。見送られた提案も再び作らない
  - 個々のプロバイダが失敗しても、植物の登録などの元の操作は失敗させない
  - 有効な提案の一覧、採用（日付の変更つき）、見送りを提供し、ユーザーの対応を記録する
  - _Requirements: 19.1, 19.2, 19.3, 19.5, 19.6, 17.6_

- [ ] 10.2 植え替えのプロバイダを作り、植物の登録・タスクの変更とつなぐ
  - 購入日つきで植物を登録したとき、植え替えタスクがなければ、適期の判定ロジックを使って植え替えタスクの提案を作る
  - 提案を採用すると、提案日（または変更後の日）を予定日とする植え替えタスクを作る
  - 植え替えタスクの予定日を避ける時期に設定したとき、「株を傷めやすい」という、やらない方がよいことの助言を作る（設定自体は妨げない）
  - 植物の登録から提案の採用・見送りまでの流れを、結合テストで確認する
  - _Requirements: 17.1, 17.2, 17.3, 17.4, 17.5, 17.6, 17.7, 17.8, 17.9_

- [ ] 11. リアルタイム同期を作る（サーバー）
- [ ] 11.1 変更イベントの発行と、サーバー間の配信を作る
  - 植物・置き場所・タスク・記録・メモ・メンバー・世帯・提案の作成・更新・削除が確定したあとに、世帯ごとの変更イベントを発行する
  - 世帯のバージョン番号を、変更のたびに同じトランザクションで1つ進める
  - データベースの通知の仕組みを使い、どの API インスタンスでもイベントを受け取れるようにする
  - _Requirements: 11.1_

- [ ] 11.2 WebSocket での購読と配信を作る
  - ID トークンで認証した WebSocket 接続を受け付け、所属を確認したうえで、指定した世帯の変更を購読させる
  - 変更イベントを、その世帯を購読しているほかの接続に転送する
  - ロールの変更・メンバーの削除を受けた接続に知らせ、削除された場合は購読をやめさせる
  - 定期的な ping で、切れた接続を片付ける
  - 完了から別の接続にイベントが届くまでを、結合テストで確認する
  - _Requirements: 11.1, 4.6, 4.7, 20.1_

- [ ] 12. 通知と定期ジョブを作る
- [ ] 12.1 定期ジョブの実行基盤と、FCM での送信を作る
  - スケジューラーから呼ばれるジョブ用のエンドポイントを作り、スケジューラーのサービスアカウントからの呼び出しだけを受け付ける
  - FCM でプッシュ通知を送る仕組みを作り、無効になった通知トークンは削除する
  - 二重に起動されても結果が変わらないようにし、ジョブごとの処理件数と所要時間をログに出す
  - _Requirements: 15.1, 16.1（の前提となる送信基盤）_

- [ ] 12.2 完了通知の送信ジョブを作る
  - 完了を記録したときに、同じトランザクションで通知のアウトボックスに積む（スキップは積まない）
  - 記録から一定時間（60秒）が過ぎたものを、世帯と作業した人ごとにまとめて1件の通知にする
  - 作業した本人と、完了通知を無効にしたメンバーには送らない
  - 送る前に取り消された記録の通知は送らない
  - 参加の通知も同じ仕組みでオーナーに送る
  - タップしたときに対象の植物を開けるよう、通知に植物の情報を含める
  - _Requirements: 16.1, 16.2, 16.3, 16.4, 16.5, 16.6, 16.7, 3.8_

- [ ] 12.3 リマインダーの送信ジョブを作る
  - 端末のタイムゾーンでリマインダーの時刻を過ぎていて、その日にまだ送っていないメンバーを抽出する
  - 世帯に今日以前の未完了タスクがある場合だけ、件数と内容の概要をまとめた1件の通知を送る
  - すべて完了またはスキップ済みの日は送らない
  - 閲覧者にも通知設定に応じて送る
  - 1日1回であることを、データベースの制約で保証する
  - タイムゾーンが異なる端末、二重の実行を含めて結合テストで確認する
