# 0001. OS に共通の UI は OS の標準部品（iOS は HIG）に任せ、アプリ固有の UI は uchinokusa のデザインシステムで作る

- 状態：採用
- 日付：2026-10-31
- 関連：要件20-6・20-7、`docs/design/screen-inventory.md`（5章 共通コンポーネント）、`docs/design/design-to-implementation.md`（② デザインの土台）、`.kiro/steering/design.md`

## 背景
- uchinokusa は iOS と Android の両方でリリースする（React Native + Expo の1つのコードベース）。要件20-6 は「両方で **同じ機能**」を求めているが、同じ見た目は求めていない
- 最初の利用者は、開発者の夫婦（どちらも iPhone）と、その家族である。家族には IT に詳しくない親世代も含む
- デザインは1人で進めるので、ゼロからすべての部品を作る余裕はない
- デザインから実装までを Claude Code（Figma MCP）で引き継ぐため、「どの部品を自作し、どれを OS に任せるか」が決まっていないと、Figma とコードの両方で迷いが出る

## 検討した案
| 案 | 内容 | 評価 |
|---|---|---|
| A. すべて自作 | タブバーや日付の選択まで、独自の見た目で作る | 作る量が多い。OS の操作感から外れ、OS のアップデート（iOS 26 の Liquid Glass など）にも追従できない |
| B. iOS の見た目を両方の OS で使う | HIG の部品を描き直して、Android でも iOS 風に見せる | iOS の利用者には自然だが、Android では異質に見える。Android 版で作り直しになる |
| C. OS ごとに完全に作り分ける | iOS は HIG、Android は Material Design で、アプリ固有の部品も別々に作る | 1人の開発では2倍の手間になる。アプリとしての統一感もなくなる |
| **D. 2つの層に分ける** | OS に共通の UI は OS の標準部品に任せ、アプリ固有の UI だけ自作のデザインシステムで作る | **採用** |

## 決定
1. **UI を2つの層に分ける**

   | 層 | 方針 | 例 |
   |---|---|---|
   | OS の層 | OS の標準部品を使う。見た目を自作しない。iOS では HIG に従い、Android では同じコードが自動で Material の見た目になる | 画面遷移とナビゲーションバー、タブバー、確認のアラート、アクションシート・メニュー、日付の選択、共有シート、スイッチ、セグメントの切り替え、検索バー、シート（モーダル）、権限のダイアログ、触覚フィードバック |
   | アプリの層 | uchinokusa のデザインシステム（トークンと部品）で作る。両方の OS で同じ見た目にする | TaskCard、CareKindIcon（作業の種類の色とアイコン）、SuggestionCard、OverdueBadge、ConditionLabel、RoleBadge、一覧の項目、カレンダーの印、空の状態、取り消しのスナックバー、トースト、QRコード |

2. **アプリの層は、HIG を基準にして作る**
   - 余白・タップ領域（44pt 以上）・文字の段階（Large Title、Title、Headline、Body、Footnote など）・コントラストは、HIG の基準に合わせる
   - 端末の文字の大きさの設定（Dynamic Type）に追従し、文字を大きくしても崩れないレイアウトにする
   - Figma では、Apple 公式の iOS の UI キットを OS の層の素材として使い、アプリの層の部品だけを自作する

3. **トークンの名前は OS に依存させない**
   - `color/accent`、`color/text/secondary` のように、役割の名前をつける（`color/ios/systemBlue` のような名前にしない）
   - 値は iOS のシステムカラーや文字の大きさを参考に決めてよい。Android 版で値だけを調整できるようにする

4. **OS の層の部品を自作しない**
   - 標準部品で表現できないことが出てきたら、自作する前に、この記録を見直す（新しい記録を追加する）

## 理由
- 最初の利用者（iPhone の夫婦と家族）にとって、OS の層が iOS の標準どおりであることが、いちばん違和感がない
- HIG はタップ領域・文字の大きさ・コントラストの基準がはっきりしていて、親世代にも使いやすい画面を、迷わずに作れる
- OS の層を OS に任せれば、作る部品の数が減り、OS のアップデートに自動で追従でき、Android 版では OS の層の作り直しが要らない
- アプリの層を共通にすることで、uchinokusa らしさ（作業の種類の色、今日やることのカード）は両方の OS で同じになる
- 「どちらの層か」が決まっているので、Figma で何を描くか・コードで何を作るかを、Claude Code が判断できる

## トレードオフ
- OS の層は、OS ごとに見た目と挙動が少し違う。スクリーンショットやサポートの説明が OS ごとに変わる
- OS の標準部品でできることに、デザインが制約される（例：アラートのボタンの色は自由に変えられない）
- Android 版の前に、アプリの層が Android の中で浮いていないかを確認する必要がある

## Android 版の前に見直すこと
- 戻る操作（Android の戻るボタン・ジェスチャー）で、シートやダイアログが正しく閉じるか
- Android の標準の書体（Roboto など）で、文字の幅があふれないか
- 押したときの反応（iOS は色が薄くなる、Android は波紋）を、アプリの層の部品でどう扱うか
- アプリの層のトークンの値（色・角丸・影）が、Material の画面の中で違和感がないか
