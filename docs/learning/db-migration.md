# データベースのマイグレーション

- 日付：2026-10-27
- きっかけ：タスク 1.3（コミット `6892060`）で作った `server/db/migrations/00001_init.sql`

## Q. マイグレーションとは？

**データベースの構造（テーブル・列・インデックス・制約など）の変更を、番号付きの SQL ファイルとして積み重ねて管理する仕組み** である。

たとえるなら **データベースの構造のための git**。git のコミットがコードの変更を1つずつ記録するように、マイグレーションのファイルは構造の変更を1つずつ記録する。

```
server/db/migrations/
  00001_init.sql            最初のテーブルをすべて作る        <- タスク 1.3
  00002_add_xxx.sql         （例）列を1つ追加する              <- 将来のタスク
  00003_add_index_yyy.sql   （例）インデックスを追加する        <- 将来のタスク
```

### どこまで適用したかを、DB 自身が覚えている

goose（このプロジェクトのマイグレーションのツール）は、DB の中に `goose_db_version` という表を作り、適用済みの番号を記録する。`migrate` を実行すると、**まだ適用していない番号だけ** を順に実行する。

```
                 00001   00002   00003
ローカルの DB      済      済      済     -> migrate しても何もしない
本番の DB          済      済      未     -> migrate すると 00003 だけ実行する
新しく作った DB    未      未      未     -> migrate すると 00001 から順にすべて実行する
```

## Q. どんな困りごと（ペイン）を解決する？

マイグレーションがないと、構造の変更を、誰かが各環境で手で実行することになる。

| ペイン | マイグレーションでどう解決するか |
|---|---|
| 「ローカルでは列を足したが、本番で `ALTER TABLE` を流し忘れた」 | `migrate` が未適用のものを必ず実行する |
| ローカル・テスト・本番の構造が少しずつずれていく | 全環境が同じファイルを同じ順で実行するので、同じ構造になる |
| 新しく参加した人が、DB を一から再現できない | 空の DB に `migrate` を実行するだけで、今の構造になる |
| 「この列はいつ、なぜ追加された？」が分からない | ファイルが git に残り、PR でレビューもできる |
| コードの変更と DB の変更が、別々にリリースされてずれる | 同じコミットに入れて、一緒にデプロイできる |

このプロジェクトでは、テストのたびに testcontainers で空の PostgreSQL を起動し、マイグレーションを適用してから結合テストを行う。これも「一から同じ構造を作れる」ことに支えられている。

フロントエンドで近いものは、ブラウザーの IndexedDB の `onupgradeneeded`（DB のバージョンが上がったときに、古いバージョンから順に構造を作り変える処理）。

## Q. `00001_init.sql` は、どのタイミングで作るもの？

**アプリで最初に DB を使う前に、1度だけ作る**。このプロジェクトでは、タスク 1.3 で設計書（`design.md` の物理データモデル）をもとに作った。MVP で使うテーブルをまとめて作るので、`init`（初期化）という名前になっている。

その後、構造を変えたくなったら、**`00001` を書き換えずに、新しいファイル（`00002_...sql`）を追加する**。

- 本番などで適用済みのファイルを書き換えても、その DB では再び実行されない（もう「済」になっているため）。書き換えた内容は、新しく作る DB にだけ反映され、環境ごとに構造がずれる
- 例外として、**まだどの共有の環境にも適用していない**うち（今の MVP の開発中など）は、`00001` を直してもよい。ローカルの DB は作り直せばよい

ファイルは手で作ってもよいし、`goose create add_xxx sql` で番号付きの空のファイルを作ることもできる。

### ファイルの中の書き方（goose の形式）

```sql
-- +goose Up
CREATE TABLE users (...);       -- 適用するときに実行する

-- +goose Down
DROP TABLE users;               -- 取り消すときに実行する（Up と逆の順番で消す）
```

- `-- +goose Up` と `-- +goose Down` は、ただのコメントではなく goose が読む印
- 関数の定義のように、中に `;` を含む文は `-- +goose StatementBegin` と `-- +goose StatementEnd` で囲む（どこまでが1つの文かを goose に教える）

### このプロジェクトでの実行のされ方

1. `server/db/db.go` の `//go:embed migrations/*.sql` で、SQL ファイルを **実行ファイルの中に埋め込む**。本番に SQL ファイルを別に置かなくてよい
2. `uchinokusa migrate` を実行すると、`server/internal/adapter/postgres/postgres.go` の `Migrate` が goose を呼び、`provider.Up` で未適用のものを適用する

## Q. PostgreSQL のマイグレーションで注意すべきことは？

### 1. 適用済みのファイルは書き換えない

上の説明のとおり。直したいときは、新しいファイルで直す。

### 2. PostgreSQL は、構造の変更もトランザクションで取り消せる（よい点）

PostgreSQL では、`CREATE TABLE` や `ALTER TABLE` もトランザクションの中で実行できる。goose は、各ファイルをトランザクションの中で実行する。途中で失敗すると、そのファイルの変更はすべて取り消され、中途半端な状態が残らない。MySQL ではこれができず、途中まで適用された状態が残ることがある。

### 3. ロックで、アプリが止まることがある

`ALTER TABLE` の多くは、そのテーブルに最も強いロックをかけ、終わるまで **読み書きをすべて待たせる**。

- 大きなテーブルで、時間のかかる変更をすると、その間アプリが止まる
- さらに怖いのは **ロックの行列**。`ALTER TABLE` 自体は一瞬で終わるものでも、長いトランザクションが動いていると、それが終わるまでロックを取れずに待つ。その間、後から来た普通の SELECT もすべて `ALTER TABLE` の後ろに並んで待たされる

```
長いトランザクション（実行中） ---------------------------->
ALTER TABLE（ロック待ち）           [待つ...................]
普通の SELECT                          [待つ.................]   <- アプリが止まって見える
普通の SELECT                            [待つ...............]
```

対策：マイグレーションの最初に `SET lock_timeout = '5s';` を書いて、ロックが取れなければすぐあきらめる（あとでやり直す）。

### 4. 時間のかかる変更と、その避け方

| やりたいこと | 注意 | 避け方 |
|---|---|---|
| インデックスを追加する | `CREATE INDEX` は、作り終わるまで書き込みを止める | `CREATE INDEX CONCURRENTLY` を使う。ただしトランザクションの中で実行できないので、goose では `-- +goose NO TRANSACTION` を付けたファイルに分ける |
| 列を追加する | 定数の初期値（`DEFAULT 0` など）なら一瞬で終わる（PostgreSQL 11 以降）。`random()` のような実行のたびに変わる初期値だと、全行を書き直す | 初期値は定数にする |
| 列の型を変える | 多くの場合、テーブル全体を書き直す | 新しい列を足して移す（下の 6 の方法） |
| 既存の列に `NOT NULL` を付ける | 全行を確かめる間、ロックする | 先に `CHECK (col IS NOT NULL) NOT VALID` を付け、別のマイグレーションで `VALIDATE CONSTRAINT` する |
| 外部キーや CHECK 制約を足す | 全行を確かめる間、ロックする | `NOT VALID` で足してから、別に `VALIDATE CONSTRAINT` する |

MVP の間はデータが少ないので、どれも一瞬で終わる。ただ、データが増えてから困らないように、習慣にしておくとよい。

### 5. 列挙値を増やしやすくする

`00001_init.sql` では、列挙値を PostgreSQL の `ENUM` 型ではなく、`text` と `CHECK` 制約で表している（ファイルの先頭のコメントのとおり）。`ENUM` 型は、値の削除や並べ替えが難しく、値の追加にも制約がある。`CHECK` なら、制約を付け直すだけで済む。

### 6. 列の名前の変更・削除は、古いアプリを壊す

Cloud Run では、デプロイの途中に **古い版と新しい版のアプリが同時に動く** 時間がある。マイグレーションで列の名前を変えると、その間に古い版がエラーになる。

そこで、**広げてから、縮める（expand / contract）** の順番で、複数回のリリースに分ける。

```
1. 新しい列を追加する                          （古い版も新しい版も動く）
2. 両方の列に書き込むアプリをリリースする
3. 古い列のデータを、新しい列にコピーする
4. 新しい列だけを読むアプリをリリースする
5. 古い列を削除する
```

これは、`api/openapi.yaml` の「項目は追加だけ行い、削除や意味の変更はしない」という互換性のルールと同じ考え方である。

### 7. Down は、本番ではあまり使わない

`-- +goose Down` の `DROP TABLE` を本番で実行すると、**データごと消える**。本番で問題が起きたときは、Down で戻すより、直すためのマイグレーションを新しく追加する（前に進めて直す）ことが多い。Down は、主にローカルでの試行錯誤に使う。

### 8. 大量のデータの書き換えは、構造の変更と分ける

「全行の値を計算し直す」のような処理を1つのトランザクションで行うと、長いロックと大きな負荷になる。構造の変更とは別に、少しずつ（たとえば1,000行ずつ）処理する。

## Q. シーディング（初期データの投入）は、いつ・どうやる？

### シーディングとは

**アプリが動くために、最初から DB に入っていてほしいデータを投入すること** である。マイグレーションが「入れ物（構造）」を作るのに対し、シーディングは「中身（データ）」を入れる。

初期データには3種類あり、扱いが違う。

| 種類 | 例 | 本番に入れる？ | このプロジェクトでは |
|---|---|---|---|
| マスタデータ | 植物マスタ（モンステラの推奨の水やり周期など） | 入れる | `seed` サブコマンドで投入する（タスク 6.1） |
| 開発用のサンプルデータ | 架空の世帯や植物 | 入れない | 今のところ予定なし |
| テスト用のデータ | 結合テストで使う世帯やユーザー | 入れない | 各テストの中で、そのテストに必要な分だけ作る |

このプロジェクトでいう「シーディング」は、1つ目の **植物マスタ** のことである（`design.md`「植物マスタの初期データ」）。

### いつやるか

**マイグレーションのあと、サーバーを起動する前**。テーブルがないとデータを入れられないので、順番が決まっている。

```
migrate（入れ物を作る） -> seed（中身を入れる） -> serve（サーバーを起動する）
```

| 環境 | タイミング |
|---|---|
| ローカル | `docker compose up -d` → `uchinokusa migrate` → `uchinokusa seed` |
| 本番 | デプロイのたびに、`migrate` のあとに `seed` を実行する（植物マスタの内容を直したら、次のデプロイで反映される） |
| テスト | 植物マスタが必要なテストでは、マイグレーションのあとに seed の処理を呼ぶ |

### どうやるか（このプロジェクトの設計）

```
server/db/seeds/species.yaml        植物マスタの中身（30〜50種、出典つき）。git で管理する
        |
        |  go:embed で実行ファイルに埋め込む（マイグレーションと同じ）
        v
uchinokusa seed                     YAML を読み、species テーブルに入れる
        |
        v
species テーブル
```

今の `main.go` では、`seed` は「未実装」のエラーを返すだけで、タスク 6.1 で実装する。

### なぜマイグレーションの中で INSERT しないのか

マイグレーションの SQL に `INSERT INTO species ...` を書くこともできる。ただし、マイグレーションは **追加しかできない履歴** なので、植物の説明を1か所直すたびに、新しいマイグレーションのファイルが増えていく。

植物マスタは、出典を見直したり種類を増やしたりと、内容がよく変わる。そのため、**今あるべき内容を YAML に1つだけ持ち、それに DB を合わせる** ほうが管理しやすい。YAML なら、差分のレビューもしやすい。

逆に、値がほとんど変わらない小さな表（国の一覧など）なら、マイグレーションで入れてしまうこともある。

### いちばん大事なこと：何度実行しても同じ結果になるようにする（冪等性）

`seed` はデプロイのたびに実行するので、**2回目以降に実行しても、データが重複したり壊れたりしてはいけない**。この性質を冪等（べきとう、idempotent）という。

単純な `INSERT` だと、実行するたびにモンステラが1件ずつ増えてしまう。そこで、**あれば更新し、なければ追加する**（upsert）。

```sql
INSERT INTO species (key, name_ja, ...)
VALUES ('monstera-deliciosa', 'モンステラ', ...)
ON CONFLICT (key) DO UPDATE
SET name_ja = EXCLUDED.name_ja, ...;
```

`ON CONFLICT` を使うには、「同じ植物かどうか」を見分ける **ユニークな列** が必要である。今の `species` テーブル（`00001_init.sql`）には、主キーの `id`（自動で作る UUID）以外にユニークな列がない。そのため、タスク 6.1 で、YAML に書く安定した識別子の列（上の例の `key` など）を、新しいマイグレーション（`00002`）で追加することになるはずである。

### ほかの注意点

- **1つのトランザクションで投入する**：途中で失敗したら、すべて取り消す。半分だけ入った状態を残さない
- **YAML から消した植物を、DB から消さない**：ユーザーの植物（`plants.species_id`）が参照している。外部キーは `ON DELETE SET NULL` なので、消すとユーザーの植物から種類の情報が外れてしまう。消す代わりに「使わない」印を付けるなどで対応する
- **ユーザーのデータを seed で作らない**：本番の seed は、全ユーザーで共通のマスタデータだけにする

フロントエンドで例えるなら、アプリに同梱する定数の JSON（選択肢の一覧など）に近い。DB に入れておくと、検索できるうえ、アプリを更新しなくても中身を直せる。
