## 1. 認証とは何か

### 認証と認可は別のもの

| | 認証（Authentication、AuthN） | 認可（Authorization、AuthZ） |
|---|---|---|
| 問い | **あなたは誰？** | **あなたは、それをしてよい？** |
| 例 | 「このリクエストは、ユーザー A からのものだ」と確かめる | 「ユーザー A は、この世帯の編集者なので、植物を追加してよい」と判断する |
| 失敗したとき | 401 Unauthorized（`unauthenticated`） | 403 Forbidden（`forbidden`） |
| このプロジェクト | タスク 2.1（Firebase の ID トークン） | タスク 4.1（オーナー・編集者・閲覧者のロール） |

建物に例えると、**認証は入口の受付で身分証を見せること**、**認可は社員証で入れる部屋が決まっていること**。このノートは、主に認証の話である。

### 本人だと示す3つの手がかり（認証の要素）

| 要素 | 例 |
|---|---|
| 知っているもの | パスワード、暗証番号 |
| 持っているもの | スマートフォン、SMS が届く電話番号、セキュリティキー |
| 本人そのもの | 指紋、顔 |

2つ以上を組み合わせるのが **多要素認証（MFA）**。パスワードが漏れても、スマートフォンがなければ入れない。

### なぜ「ログインした状態」を保つ仕組みが必要か

HTTP は、**1つ1つのリクエストが独立している**（ステートレス）。サーバーは、前のリクエストが誰からだったかを覚えていない。毎回パスワードを送るわけにはいかないので、ログインに成功したら「通行証」を渡し、以降のリクエストではそれを見せてもらう。この通行証の方式が、3章の「セッション」と「トークン」である。

## 2. 世の中にある認証方法

ユーザーが「自分が本人だ」と示す手段。

### 2-1. ID とパスワード

いちばん昔からある方法。

- **サーバーの仕事**：パスワードをそのまま保存せず、元に戻せない形（ハッシュ。bcrypt や Argon2 など）にして保存する。ログインのときは、入力をハッシュにして比べる
- **よい点**：どこでも使える。外部のサービスに頼らない
- **困る点**
  - ユーザーが覚えなければならない。同じパスワードを使い回しやすく、ほかのサービスから漏れたパスワードで入られる
  - パスワードを忘れたときの再設定（メールの送信など）も作る必要がある
  - 保存を間違えると、漏えいしたときの被害が大きい

### 2-2. マジックリンク・メールのワンタイムコード

メールアドレスを入力すると、ログイン用のリンクや6桁のコードがメールで届く。

- **よい点**：パスワードを覚えなくてよい
- **困る点**：毎回メールを開く手間がある。ネイティブアプリでは、メールのリンクからアプリに戻す設定（ディープリンク）が必要。メールアドレスを預かることになる

### 2-3. SMS のワンタイムコード

電話番号に6桁のコードが届く。

- **よい点**：電話番号があれば使える
- **困る点**：SMS の送信に費用がかかる。電話番号を乗っ取る攻撃（SIM スワップ）に弱い。電話番号という個人情報を預かる

### 2-4. ソーシャルログイン（「Google でログイン」「Apple でサインイン」）

すでに持っている Google や Apple のアカウントで、本人だと示す。裏側では **OAuth 2.0** と **OpenID Connect（OIDC）** という標準の仕組みが使われている。

- **OAuth 2.0**：もとは「ほかのアプリに、自分のデータへのアクセスを許す」ための仕組み（認可）
- **OpenID Connect**：OAuth 2.0 の上に、「この人は誰か」を伝える **ID トークン** を足したもの（認証）

```
ユーザー          アプリ                    Google / Apple
  |  「Google でログイン」 |                        |
  |--------------------->|                        |
  |                      |-- ログイン画面を開く ---->|
  |<---------------- Google のログイン画面 ----------|
  |-- 本人だと確かめる（Google のパスワード、顔認証など） -->|
  |                      |<-- ID トークン（この人は誰か）--|
  |                      |  （署名つきの証明書のようなもの）
```

- **よい点**：パスワードを新しく作らなくてよい。2段階認証などの強い守りは、Google や Apple が受け持つ。ボタン1つで済む
- **困る点**：Google や Apple のアカウントを持っていない人は使えない。ログインの成否が外部のサービスに左右される

**Sign in with Apple の特徴**：メールアドレスを隠す機能（Apple が作る転送用のアドレスを渡せる）がある。名前は最初のサインインのときにしか受け取れない。

### 2-5. パスキー（Passkey）

パスワードの代わりに、端末の中の **鍵のペア** を使う新しい方法（WebAuthn / FIDO2 という標準）。

- 端末が「秘密鍵」を持ち、サーバーには「公開鍵」だけを預ける。ログインのたびに、端末が秘密鍵で署名し、サーバーが公開鍵で確かめる
- 秘密鍵は端末から出ない。使うときに、指紋や顔で端末のロックを外す
- **よい点**：覚えるものがない。偽のサイトに入力させる攻撃（フィッシング）が効かない。サーバーから漏れても公開鍵しかない
- **困る点**：比較的新しく、端末をなくしたときの復旧の考え方がまだ分かりにくい。対応していないサービスや端末もある

### 2-6. 生体認証（指紋・顔）

アプリでの「Face ID でログイン」は、**指紋や顔のデータをサーバーに送っているわけではない**。端末が本人を確かめて、端末の中に保存した鍵や通行証を使えるようにしているだけである。単独の認証方法というより、ほかの方法の「鍵を開ける手段」。

### 2-7. 匿名認証（ゲスト）

ログインの操作なしで、とりあえずの ID を発行する。あとで Google などと結び付けて、正式なアカウントにできる。

- **よい点**：アプリをすぐ試せる
- **困る点**：端末を変えると、データを引き継げない。家族と共有するには、結局正式なアカウントが要る

### 2-8. 企業向けの SSO（SAML、OIDC）

会社のアカウント（Okta、Microsoft Entra ID など）で、業務のサービスにまとめてログインする。B2B（企業向け）のサービスで使う。家庭向けのアプリには関係が薄い。

## 3. ログインした状態を保つ方式

本人だと確かめたあと、2回目以降のリクエストで「誰か」を示す方法。

### 3-1. セッション方式（サーバーが覚える）

```
1. ログインに成功する
2. サーバーは「セッション ID: abc123 = ユーザー A」を、サーバー側（DB や Redis）に保存する
3. ブラウザーに Cookie で「abc123」を渡す
4. 以降のリクエストでは、ブラウザーが自動で Cookie を送る
5. サーバーは、保存しておいた表から「abc123 = ユーザー A」と引く
```

- **例え**：クロークの番号札。札には番号しか書いておらず、荷物（ユーザーの情報）はお店が預かっている
- **よい点**：サーバーの表から消せば、すぐにログアウトさせられる
- **困る点**：サーバーが複数台なら、全台から同じ表を見られるようにする必要がある（Redis などを用意する）

Web のサービス（Rails、Laravel など）では、今もこの方式が多い。

### 3-2. トークン方式（トークン自体に情報を書く）

```
1. ログインに成功する
2. サーバー（または認証サービス）は「ユーザー A、1時間有効」と書いたトークンに署名して渡す
3. アプリは、以降のリクエストで「Authorization: Bearer <トークン>」ヘッダーに付けて送る
4. サーバーは、署名が正しいか、期限が切れていないかを確かめるだけで、ユーザー A だと分かる
```

- **例え**：偽造できない印のある入館証。受付の名簿を見なくても、入館証そのものを見れば本人と有効期限が分かる
- **よい点**：サーバーは表を持たなくてよい（ステートレス）。サーバーが何台あっても、それぞれが単独で確かめられる
- **困る点**：一度渡したトークンは、期限が来るまで有効。すぐに無効にしたい場合は、別の仕組みが要る

よく使われるのが **JWT（JSON Web Token）** という形式。`ヘッダー.中身.署名` の3つを `.` でつないだ文字列で、中身は誰でも読める（暗号化ではなく、改ざんを防ぐ署名）。

### 3-3. アクセストークンとリフレッシュトークン

トークンは盗まれると悪用されるので、有効期限を短くしたい。でも、短いと何度もログインし直すことになる。そこで2つを組み合わせる。

| | アクセストークン（Firebase では ID トークン） | リフレッシュトークン |
|---|---|---|
| 用途 | API のリクエストに付ける | 新しいアクセストークンをもらう |
| 有効期限 | 短い（Firebase では1時間） | 長い（明示的に取り消すまで） |
| 送る先 | API サーバー（このプロジェクトの Go のサーバー） | 認証サービス（Firebase）だけ |

アプリは、アクセストークンの期限が切れそうになると、リフレッシュトークンで新しいものをもらう。ユーザーは何もしなくてよい。アプリを再起動してもログインしたままなのは、リフレッシュトークンを端末に安全に保存しているからである（要件1-4）。

### 3-4. Web とネイティブアプリの違い

| | Web（ブラウザー） | ネイティブアプリ（iOS / Android） |
|---|---|---|
| 通行証の置き場所 | Cookie が基本 | 端末の安全な保管庫（iOS の Keychain、Android の Keystore） |
| 送り方 | ブラウザーが Cookie を自動で送る | アプリが `Authorization` ヘッダーに付ける |
| 主な方式 | セッション方式が多い | トークン方式が多い |

ネイティブアプリには、ブラウザーのような Cookie の自動の仕組みがないので、トークン方式との相性がよい。

### 3-5. 人ではなく、プログラムの認証

| 方式 | 使いどころ |
|---|---|
| API キー | 外部の API を使うとき（天気の API など）。キーを知っていれば誰でも使えるので、漏らさないことが前提 |
| サービスアカウントの OIDC トークン | クラウドのサービス同士。このプロジェクトでは、Cloud Scheduler がジョブのエンドポイントを呼ぶときに使う（`design.md`） |

## 4. 認証の作り方の選択肢

| 選択肢 | 例 | よい点 | 困る点 |
|---|---|---|---|
| すべて自分で作る | Go でパスワードのハッシュ、セッションの表、パスワードの再設定を実装 | すべてを理解でき、外部に頼らない | 作る量が多く、間違えると重大な事故になる |
| ライブラリを使って自分で動かす | Ory Kratos、Keycloak など | 自分のサーバーで動かせる | 運用（更新・監視）が必要 |
| 認証のサービス（IDaaS）に任せる | Firebase Auth、Auth0、Amazon Cognito、Supabase Auth、Clerk | ログインの画面や SDK、トークンの更新まで用意されている | 料金と、サービスへの依存（乗り換えにくさ） |

## 5. Firebase の基礎

### 5-1. Firebase とは

**Google が提供する、アプリ開発のためのサービスの詰め合わせ**（BaaS：Backend as a Service）。Google Cloud の上に作られていて、1つの Firebase プロジェクトは、1つの Google Cloud プロジェクトと結び付いている。

| サービス | できること | このプロジェクトで使う？ |
|---|---|---|
| **Authentication** | ログイン（Apple、Google、メール、電話番号など） | **使う**（タスク 2.1） |
| **Cloud Messaging（FCM）** | プッシュ通知の配信 | **使う**（タスク 2.2 以降） |
| **Hosting** | 静的なファイルの配信 | **使う**（招待リンクの検証ファイル） |
| Firestore / Realtime Database | アプリから直接読み書きできる DB | 使わない（Go のサーバーと PostgreSQL を使う） |
| Cloud Functions | サーバーレスの関数 | 使わない（Go のサーバーを Cloud Run で動かす） |
| Storage | 画像などのファイルの保存 | 使わない（MVP では写真を扱わない） |
| Crashlytics、Analytics など | クラッシュの収集、利用の分析 | 未定 |

Firebase だけでアプリのバックエンドを丸ごと作ることもできる。ただ、このプロジェクトは「バックエンドを学びたい」という目的があるので、**認証とプッシュ通知の配信だけを任せ、データとロジックは自分の Go のサーバーで持つ** 方針にしている（`tech.md`）。

### 5-2. Firebase Auth がしてくれること

1. **ログインの方法をまとめる**：Apple、Google、メール、電話番号など、どの方法でログインしても、**同じ形の ID トークン** と **同じ形のユーザー ID（UID）** にそろえる
2. **トークンを管理する**：ID トークン（1時間）とリフレッシュトークンを発行し、アプリの SDK が自動で更新・保存する
3. **ユーザーの一覧を持つ**：Firebase のコンソールで、ユーザーの一覧や、どの方法でログインしたかを見られる

いちばん大事なのは 1。Apple と Google の ID トークンは、発行元も形式も少しずつ違う。Firebase を通すと、**Go のサーバーは Firebase の ID トークンという1種類だけを確かめればよい**。

### 5-3. ログインからリクエストまでの流れ（このプロジェクト）

```
 アプリ（React Native）        Apple / Google          Firebase Auth             Go のサーバー            PostgreSQL
      |                            |                        |                         |                       |
 1.   |-- Apple でサインイン ------->|                        |                         |                       |
      |<-- Apple の資格情報 ---------|                        |                         |                       |
 2.   |-- 資格情報を渡す ------------------------------------>|                         |                       |
      |<-- Firebase の ID トークン（1時間）+ リフレッシュトークン --|                         |                       |
      |    （SDK が Keychain / Keystore に保存する）             |                         |                       |
 3.   |-- GET /v1/me  Authorization: Bearer <ID トークン> ------------------------------>|                       |
      |                            |                        |                         | 4. 署名・期限・発行先を確かめる
      |                            |                        |<-- 公開鍵を取得（キャッシュ）-|                       |
      |                            |                        |                         | 5. uid でユーザーを探す --->|
      |                            |                        |                         |    いなければ作る         |
      |<------------------------------------------------- 200 { ユーザーの情報 } -------|                       |
 6. （1時間たつと）SDK がリフレッシュトークンで新しい ID トークンをもらい、以降はそれを付ける
```

ポイント：

- **Go のサーバーは、パスワードも Apple の資格情報も見ない**。見るのは、Firebase が署名した ID トークンだけ
- 4 で、サーバーは Firebase に毎回問い合わせない。Google が公開している **公開鍵** で、署名を手元で確かめる（公開鍵はしばらくキャッシュする）
- ユーザーの情報（表示名など）は、自分の DB（`users` テーブル）に持つ。Firebase とは `firebase_uid` の列で結び付ける

### 5-4. Firebase の ID トークンの中身

ID トークンは JWT である。`.` で区切られた3つの部分を、それぞれ Base64URL で戻すと、次のような中身になる（値は例）。

```
ヘッダー： { "alg": "RS256", "kid": "（どの公開鍵で確かめるか）" }

中身：     {
             "iss": "https://securetoken.google.com/demo-uchinokusa",   // 発行者
             "aud": "demo-uchinokusa",                                  // 宛先（Firebase のプロジェクト ID）
             "sub": "Xy12...",                                          // ユーザーの UID
             "iat": 1793232000,                                         // 発行した時刻
             "exp": 1793235600,                                         // 期限（発行から1時間）
             "name": "たろう",
             "firebase": { "sign_in_provider": "apple.com" }
           }

署名：     Google の秘密鍵で、ヘッダーと中身に付けた署名
```

サーバーが確かめること（Firebase Admin SDK の `VerifyIDToken` が行う）：

| 確かめること | 防いでいること |
|---|---|
| 署名が Google の公開鍵で正しいか | 中身を書き換えた、偽のトークン |
| `exp` が過ぎていないか | 盗まれた古いトークンの使い回し |
| `iss` と `aud` が自分のプロジェクトか | ほかの Firebase プロジェクト（ほかのアプリ）向けのトークン |
| `sub`（UID）が空でないか | 不完全なトークン |

**中身は誰でも読める** ことに注意。秘密の情報をトークンに入れてはいけない。また、トークンそのものが「入館証」なので、ログに出したり、HTTPS 以外で送ったりしてはいけない。

### 5-5. UID とは

Firebase がユーザーごとに発行する、変わらない ID。同じ人が何度ログインしても同じ。このプロジェクトでは `users.firebase_uid` に保存し、自分の DB のユーザー（`users.id`、UUIDv7）と結び付けている。

自分の DB の ID を別に持つのは、Firebase に依存する部分を `firebase_uid` の1列に閉じ込めるため。ほかのテーブル（世帯のメンバーなど）は、自分の `users.id` を参照する。将来、認証のサービスを替えても、影響はこの列に限られる。

### 5-6. ログアウトとアカウントの削除で気をつけること

トークン方式なので、**一度発行した ID トークンは、期限（最大1時間）まで有効** なままである。

- アプリでログアウトすると、端末のトークンは消える。ただ、もし誰かがトークンを盗んでいたら、その人は期限まで使える
- Firebase には、取り消したトークンを拒否する確認（`VerifyIDTokenAndCheckRevoked`）もある。ただし、リクエストのたびに Firebase への問い合わせが増える
- このプロジェクトでは、MVP ではこの確認をしない。アカウントの削除では、DB の `deleted_at` を見て止める（`docs/decisions/0005-authentication.md`）

### 5-7. Firebase Auth Emulator

本物の Firebase の代わりに、手元で動く偽物（エミュレーター）。

- プロジェクト ID を `demo-` で始めると、本物の Firebase のプロジェクトなしで動く（`docs/decisions/0002`）
- 環境変数 `FIREBASE_AUTH_EMULATOR_HOST` があると、Admin SDK はエミュレーターのトークンを受け入れる
- エミュレーターのトークンには署名がない。**本番でこの環境変数を設定してはいけない**（署名のないトークンを受け入れてしまう）

### 5-8. 料金

電話番号（SMS）以外のログインは、小規模なアプリなら無料の範囲で使える。SMS は送信ごとに費用がかかる。料金の細かい条件は変わることがあるので、公開前に公式の料金ページで確認する。

## 6. このプロジェクトのコードでの流れ

タスク 2.1 で実装された部分（`server/internal/`）。

```
リクエスト（Authorization: Bearer <ID トークン>）
   |
   v
withAuth（adapter/httpapi/auth.go）           /v1 のすべてのエンドポイントにかかる。/healthz にはかからない
   |-- bearerToken：ヘッダーからトークンを取り出す。なければ 401
   |-- verifier.Verify（adapter/firebase/verifier.go）
   |      Firebase Admin SDK の VerifyIDToken で、署名・期限・発行先を確かめる
   |      だめなら 401。公開鍵を取得できないときは、トークンではなくサーバーの問題なので 500
   |-- accounts.SignIn（app/account.go）
   |      firebase_uid でユーザーを探し、いなければ作る。削除済みなら 401
   |-- context にユーザーを入れる
   v
各エンドポイント（例：GET /v1/me）
   currentUser(ctx) で、リクエストしたユーザーを取り出す
```

- 認証は、エンドポイントごとではなく、**ミドルウェアで全体にかける**。エンドポイントを追加しても、認証のかけ忘れが起きない
- `TokenVerifier` はインターフェースなので、テストでは偽物に差し替えられる。Firebase に依存するコードは `adapter/firebase` に閉じ込めている
- `api/openapi.yaml` にも、全体の `security`（`firebaseIdToken`、Bearer の JWT）として書いてある
- 401 のときは `WWW-Authenticate: Bearer` ヘッダーを付ける（HTTP の決まり）。アプリは、ID トークンを更新して1回だけ送り直し、それでもだめならサインイン画面に戻す（`design.md` のエラー処理）

## 7. このプロダクトにとって、どの方法がベストか

### 7-1. まず、このプロダクトの条件を整理する

| # | 条件 | 出どころ |
|---|---|---|
| 1 | iOS と Android のネイティブアプリ（React Native / Expo） | `product.md`、`tech.md` |
| 2 | 使う人は家族。実家の親など、IT に詳しくない人も含む | `product.md`（対象ユーザー） |
| 3 | 新しいパスワードを管理させない。Apple か Google でサインインしたい | 要件1（目的、受け入れ基準1） |
| 4 | 再起動してもログインしたまま | 要件1-4 |
| 5 | 自分の Go のサーバーと PostgreSQL でデータを持つ。Cloud Run で、台数が増えたり0になったりする | `tech.md`、`design.md` |
| 6 | 開発者は1人。認証の事故は避けたい。一方で、バックエンドは学びたい | `product.md`、メモ（学習志向） |
| 7 | 個人情報はできるだけ持たない。メールアドレスは保存しない | `design.md`（セキュリティ） |
| 8 | プッシュ通知に FCM を使う（Firebase のプロジェクトはどうせ作る） | `tech.md` |
| 9 | App Store の審査のルール | 下で説明 |

**App Store の審査のルール**（条件9）について：

- iOS アプリで Google などのソーシャルログインを提供する場合、Apple は「同等にプライバシーに配慮したログインの方法」も用意することを求めている（App Store Review Guideline 4.8）。Sign in with Apple を用意するのが、いちばん確実な対応である
- アカウントを作れるアプリは、アプリの中からアカウントを削除できなければならない（Guideline 5.1.1(v)）。Sign in with Apple を使う場合は、削除のときに Apple のトークンも取り消す（`design.md` のアカウントの削除、タスク 13.1）

ルールの細かい文言は改定されることがあるので、公開前に最新の Guideline を確認する。

### 7-2. 「認証方法」の比較

★は、このプロダクトへの合い方（3段階）。

| 方法 | 家族の使いやすさ（条件2・3） | 安全性 | 作る・運用する手間（条件6） | 個人情報（条件7） | 合い方 |
|---|---|---|---|---|---|
| **Apple / Google のソーシャルログイン** | ボタン1つ。スマホにはたいていどちらかのアカウントがある | 2段階認証などは Apple / Google が受け持つ | SDK があり少ない | メールを保存しなくてよい | ★★★ |
| ID とパスワード | 覚える・忘れる・使い回す。親世代には負担 | 漏えい・使い回しの危険 | 再設定のメールなども必要で多い | メールが必要 | ★ |
| マジックリンク・メールのコード | 毎回メールを開く手間 | 中程度 | ディープリンクの設定が必要 | メールが必要 | ★ |
| SMS のコード | 分かりやすい | SIM スワップに弱い | 送信の費用がかかる | 電話番号が必要 | ★ |
| パスキー | 慣れれば最も楽 | 最も強い | 対応がまだ広がり途中 | 持たなくてよい | ★★（将来の候補） |
| 匿名認証 | 最も楽 | 端末をなくすと終わり | 少ない | 持たない | ★（家族と共有できない） |

→ **Apple / Google のソーシャルログイン** が、条件2・3・7 にいちばん合う。要件1 でもそう決めている。

### 7-3. 「状態を保つ方式」の比較

| 方式 | このプロダクトでは |
|---|---|
| セッション（Cookie と、サーバーの表） | ネイティブアプリでは Cookie の利点が薄い。Cloud Run の複数台で表を共有するには、Redis などを別に用意する必要がある（条件5） |
| **トークン（JWT の ID トークンと、リフレッシュトークン）** | 各サーバーが公開鍵だけで確かめられ、表が要らない。台数が増えても0になっても困らない。アプリは `Authorization` ヘッダーに付けるだけ（条件1・5）。WebSocket の接続でも同じトークンを使える |

→ **トークン方式** が合う。弱点の「すぐに無効にできない」は、ID トークンの期限が1時間と短いことと、削除したユーザーを DB の `deleted_at` で止めることで補う。

### 7-4. 「作り方」の比較

| 作り方 | よい点 | このプロダクトでの困る点 | 合い方 |
|---|---|---|---|
| **Firebase Auth** | Apple と Google を1種類の ID トークンにそろえる。アプリの SDK がトークンの更新・保存までする。Emulator で手元で試せる。FCM と同じプロジェクトで管理できる（条件8）。小規模なら無料 | Firebase への依存。ID トークンの即時の取り消しには追加の確認が要る | ★★★ |
| Apple / Google の ID トークンを、Go で直接確かめる（Firebase なし） | 外部のサービスに頼らない。OIDC を深く学べる | 2種類のトークンの検証、自前のトークンの発行・更新・保存、アプリ側のつなぎ込みをすべて作る。間違えると事故になる（条件6） | ★★（学習目的なら面白いが、MVP には重い） |
| Auth0 / Clerk | 機能が豊富で、管理画面も使いやすい | ユーザーが増えると料金が上がりやすい。FCM のために Firebase は結局使う | ★★ |
| Amazon Cognito | AWS のサービスと相性がよい | このプロジェクトは Google Cloud。設定が複雑 | ★ |
| Supabase Auth | Supabase の PostgreSQL と一体で使いやすい | DB は自分で持つ方針なので、利点を生かしにくい | ★★ |
| すべて自分で作る（パスワード＋セッション） | 学習の量は最大 | 7-2 のとおり、方法そのものが家族に合わない | ★ |

### 7-5. 結論

**Firebase Auth を使い、Apple と Google でサインインする。アプリは Firebase の ID トークン（JWT）を `Authorization: Bearer` で送り、Go のサーバーが Firebase Admin SDK で確かめる。ユーザーの情報と権限（認可）は、自分の PostgreSQL で持つ。**

理由をまとめると：

1. **家族が迷わない**：ボタン1つで、新しいパスワードが要らない（条件2・3）
2. **審査のルールに合う**：Sign in with Apple を用意すれば、Guideline 4.8 にいちばん確実に合う（条件9）
3. **サーバーの作りに合う**：トークン方式なので、Cloud Run が何台でも、表を共有せずに確かめられる（条件5）
4. **事故を避けつつ、学びは残る**：パスワードの保存やトークンの発行という、間違えると危ない部分は Firebase に任せる。一方で、トークンの検証、ユーザーの作成、ミドルウェアの設計、認可（ロール）は自分の Go のコードで書く（条件6）
5. **個人情報が少ない**：DB に持つのは表示名と Firebase の UID、ログインの方法だけ（条件7）
6. **Firebase はどうせ使う**：プッシュ通知の FCM のために、Firebase のプロジェクトは必要（条件8）

### 7-6. この選択の弱点と、その手当て

| 弱点 | 手当て |
|---|---|
| Firebase（Google）に依存する | Firebase に触れるコードを `adapter/firebase` と `users.firebase_uid` の1列に閉じ込めている。乗り換えるときの影響を小さくする |
| ID トークンは、ログアウトしても最大1時間有効 | 期限が短い。アカウントの削除は DB の `deleted_at` で止める |
| Apple は名前を最初の1回しか渡さず、渡さないこともある | 表示名が空でも作れるようにし、アプリで設定を促す（要件1-2、`docs/decisions/0005`） |
| Apple / Google のアカウントがない人は使えない | MVP の対象（開発者の家族）では問題にならない。一般公開のときに、パスキーやメールの追加を検討する |
| エミュレーターの設定が本番に入ると危ない | 本番の環境変数に `FIREBASE_AUTH_EMULATOR_HOST` を入れない |
