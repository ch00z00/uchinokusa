# デザインシステム

- 日付：2026-10-31
- きっかけ：`docs/design/design-to-implementation.md` の「② デザインの土台」は、デザインシステムの構築のことか

## まとめ（自分の言葉で）

### デザインシステムとは
UI構築のために、要件や仕様から「決まった材料」と、その材料の「使い方のルール」をまとめたもの
- → デザインの統一感
- → 挙動、UI / UX の統一感
- → 要件仕様・デザイナー・エンジニアの認識の統一
- → コーディングエージェントとデザインツール間での認識の統一

### プロセス
各工程の詳しい方針と図は `docs/design/design-to-implementation.md` にある。

**① 要件仕様を定義する**
- ここで仕様定義から画面の洗い出しもやる
- 設計も込みでやる
- 必要なすべての画面をリストアップする

**② デザインの土台を作る**
- ここではデザインと実装で一貫して使う共通認識を作る
    - 変数（トークン）と部品を先に作る
        - トークン：色・余白・フォントサイズなどに変数名をつけたもの
        - 部品：トークンを組み合わせた、再利用可能で汎用的な UI コンポーネント
    - パターン：導線や挙動のルールを作る
        - 「削除前には必ずこの確認ダイアログを出す」「エラーメッセージはこう表示する」など
    - ガイドラインとしてまとめる
        - どのトークンや部品を、いつ、どう使うかを示す
            - 「赤は取り消せない操作でのみ使う」など

**③ ワイヤーフレームを作る**
- 画面ごとの仕様（画面の洗い出し）をもとに、②の部品を並べて各画面のフレームを作る
    - 目的は、配置と情報の優先順位を決めること。見た目の作り込みはしない
    - 新しい図形は描かず、②の部品とトークンだけで組む
    - 通常の状態だけでなく、空・読み込み中・エラー・閲覧者など、状態ごとにフレームを作る
    - フレーム名は画面 ID（`TODAY-01` など）にそろえる
    - Claude Code に Figma MCP で下書きを書かせ、人が見直す

**④ 仕上げる**
- ワイヤーフレームを、実装に渡せる完成形のデザインにする
    - 色・余白・文字の最終調整と、使いやすさの判断は人が行う
    - 仕様の不足や矛盾に気づいたら、①に戻して仕様と画面の洗い出しを直す（Figma だけを直さない）
    - 新しい部品が必要になったら、②に戻して部品として追加する（画面の中だけで作らない）

**⑤ フロントエンドを実装する**
- 完成したデザインを、コーディングエージェントが Figma MCP で読み取って実装する
    - Figma の変数・部品と同じ名前のトークン・部品を、コードでも使う（色などの生の値を書かない）
    - Figma MCP が返すコードの例は Web 向けなので、React Native に置き換える
    - 実装のルール（ステアリング）を先に書いておき、エージェントが毎回それに従うようにする
    - 文言は直書きせず、i18n のキーから引く
    - 1タスクずつ、「何を・なぜ」を確認しながら進める

**⑥ デザインと実装の整合性をテストする**
- 実装した画面がデザインと一致しているかを確かめる
    - シミュレーターの画面と Figma のスクリーンショットを、状態ごとに見比べる
    - iOS と Android の両方で確認する
    - 実装のずれなら⑤で、デザインの問題なら④で直す
    - 実機で初めて気づいた問題（文字があふれる、押しにくいなど）は Figma にも反映し、デザインとコードをずらさない

---

以下は、このまとめのもとになった質問と答え。

## Q. 「デザインの土台」は、デザインシステムの構築のこと？

そのとおり。②の「変数（トークン）と部品を先に作る」は、**このアプリ用の小さなデザインシステムを作る**ことである。

## Q. そもそも、デザインシステムとは何？

**画面を作るときの「決まった材料」と「使い方のルール」をまとめたもの**である。デザイナーとエンジニアが同じ材料を使うことで、どの画面も同じ見た目・同じ挙動になる。

### 料理に例えると

| 料理 | デザインシステム | uchinokusa の例 |
|---|---|---|
| 調味料の分量の基準（大さじ1 = 15ml） | **デザイントークン**：色・余白・文字の大きさなどの値に名前をつけたもの | `color/care/watering`、`space/md` |
| 下ごしらえした食材・決まったソース | **部品（コンポーネント）**：トークンを組み合わせた、繰り返し使う UI | `TaskCard`、`CareKindIcon`、`ConfirmDialog` |
| 盛りつけのルール | **パターン**：部品の組み合わせ方の決まりごと | 「削除の前には必ず確認のダイアログ」「完了のあとは取り消しのスナックバー」 |
| レシピ本 | **ガイドライン**：いつ・どう使うかの説明 | 「赤は取り消せない操作だけに使う」 |

料理人ごとに調味料の量がばらばらだと、同じメニューでも毎回味が変わる。画面も同じで、画面ごとに色や余白を目分量で決めると、少しずつ違うものが増えていく。

### 層にすると

```
  ┌────────────────────────────────────────────┐
  │ 画面        TODAY-01（今日やること）          │  ← 部品を並べて作る
  ├────────────────────────────────────────────┤
  │ パターン    完了 → 取り消しのスナックバー       │  ← 部品の組み合わせ方
  ├────────────────────────────────────────────┤
  │ 部品        TaskCard / Button / Badge        │  ← トークンを使って作る
  ├────────────────────────────────────────────┤
  │ トークン    色・余白・文字・角丸・影            │  ← いちばん下の材料
  └────────────────────────────────────────────┘
```

下の層を変えると、上の層すべてに反映される。たとえば「水やりの色を少し濃くする」ときは、トークンを1か所直すだけで、カード・カレンダー・アイコンのすべてが変わる。

## Q. トークンとは何？ ただの変数とどう違う？

仕組みとしては、ただの変数である。違いは **名前のつけ方** にある。

| 書き方 | 例 | 問題 |
|---|---|---|
| 生の値 | `#4A90D9` | 何の色かわからない。同じ色を20か所に書くと、変えるときに20か所直す |
| 見た目の名前 | `blue500` | 「水やりの色を緑に変えたい」とき、`blue500` という名前のまま緑にするわけにいかない |
| **役割の名前（セマンティック）** | `color/care/watering` | 何に使う色かがわかる。中身の値を変えても名前はそのまま使える |

そこで、2段に分けるのが一般的である。

```
  基本のトークン（パレット）         役割のトークン                   使う場所
  blue/500 = #4A90D9    ───────>  color/care/watering   ───────>  TaskCard のアイコン
  red/600  = #D93A3A    ───────>  color/danger          ───────>  削除のボタン
  gray/900 = #1A1A1A    ───────>  color/text/primary    ───────>  本文
```

ダークモードは、役割のトークンの「中身」を切り替えるだけで作れる（`color/text/primary` を、ライトでは `gray/900`、ダークでは `gray/50` にする）。

### フロントエンドで例えるなら

| フロントエンドの経験 | デザインシステムでの名前 |
|---|---|
| CSS 変数（`--color-primary`）、Tailwind の `theme` の設定 | トークン |
| 自作の `<Button variant="danger" size="sm">` | 部品とそのバリアント |
| Storybook | 部品のカタログ（どんな部品・状態があるかを並べて見る場所） |
| MUI、Chakra UI、shadcn/ui | 他社が作ったデザインシステムを、部品のライブラリとして使っているもの |

フロントエンドで `theme.ts` と `components/` を作ったことがあれば、それはすでにデザインシステムの「コード側の半分」を作っていたことになる。デザインシステムは、それを **Figma 側にも同じ名前で持ち、両方をそろえる** ものである。

## Q. 有名なデザインシステムは？

| 名前 | 作ったところ | 特徴 |
|---|---|---|
| Material Design | Google | Android の標準。部品とガイドラインが非常に細かい |
| Human Interface Guidelines | Apple | iOS の標準。部品の挙動や、触り心地のルールが中心 |
| Carbon、Polaris、Spectrum など | IBM、Shopify、Adobe | 自社の多くの製品で見た目をそろえるためのもの |

大企業のものは、何十人ものチームが何年もかけて作っている。uchinokusa に必要なのは、その **ごく小さな版** である。

## Q. uchinokusa では、どこまで作ればいい？

1人で、MVP のために作るので、**最小限から始めて、必要になったら足す**。

| 作る | 作らない（今は） |
|---|---|
| 色：基本のパレット、役割の色（文字・背景・境界線・危険・成功）、**作業の種類の5色** | 細かい色の段階をすべて揃えること |
| 文字：4〜5段階（見出し・本文・補足など）。親世代でも読める大きさ | 多くの書体の使い分け |
| 余白・角丸：4〜5段階（`xs`〜`xl`） | 影の細かい段階 |
| 部品：`screen-inventory.md` の5章の部品（約30個）。まずは③で使う分から | 使う予定のない汎用の部品 |
| パターン：確認のダイアログ、取り消しのスナックバー、空の状態、エラーの状態 | 文章のトーンの細かいガイド |
| iOS / Android の標準の部品（日付の選択、共有シート）は、OS のものを使う | OS の部品の作り直し |

### このアプリで、とくに効くところ

- **作業の種類の5色とアイコン**：今日の一覧、植物の詳細、履歴、カレンダーのすべてに出てくる。最初に決めておかないと、画面ごとに色がずれる。
- **状態のバリアント**：TaskCard の「通常 / 期限切れ / 今日は不要 / 条件つき / 閲覧者」のように、同じ部品の状態が多い。部品のバリアントにしておけば、どの画面でも同じ見せ方になる。
- **Claude との引き継ぎ**：Figma の名前とコードの名前がそろっていれば、Figma MCP で読み取ったときに、Claude は `#4A90D9` ではなく `theme.color.care.watering` と書ける。名前がそろっていないと、生の値がコードにばらまかれる。

## Q. Figma とコードでは、何が対応する？

| デザインシステムの要素 | Figma | コード（`mobile/`） |
|---|---|---|
| トークン | 変数（Variables）。モードでライト / ダーク | `src/theme/` のオブジェクト |
| 部品 | コンポーネント | `src/components/*.tsx` |
| 部品の状態 | バリアント（`state=overdue`） | props（`state="overdue"`） |
| カタログ | 部品を並べたページ | （必要になったら）Storybook |

この対応を `docs/design/design-to-implementation.md` の3章「名前をそろえる」にまとめている。
