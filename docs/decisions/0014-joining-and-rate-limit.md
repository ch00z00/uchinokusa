# 0014. 無効な招待は理由によらず 410 にし、参加はトランザクションで行い、確認と参加に利用者ごとのレート制限をかける

- 状態：採用
- 日付：2026-11-03
- 関連：タスク 5.2、`server/internal/adapter/postgres/invitations.go`、`server/internal/adapter/httpapi/ratelimit.go`、要件3-3・3-5・3-6・3-8・20-3

## 決定
1. **トークンとコードは、同じパス（`/invitations/{tokenOrCode}`）で受け付ける**
   - 空白とハイフンを除いて大文字にした結果が、使える文字だけの8文字ならコード、そうでなければトークンとして扱う。トークン（43文字）とは長さが違うので取り違えない
   - コードは手入力なので、小文字・空白・ハイフン（`k7mp-2qxa`）も受け付ける
2. **期限切れ・取り消し済み・存在しない招待は、区別せずに `410 invitation_invalid` にする**
   - 区別すると、総当たりする人に「このコードは存在する（期限が切れているだけ）」と知らせてしまう
3. **確認（`GET`）では、すでにメンバーかどうか（`alreadyMember`）も返す**。参加（`POST`）では、すでにメンバーなら `409 already_member` を返し、重複して追加しない（要件3-6）
   - オーナーが自分の世帯の招待を使っても、ロールは変わらない（`ON CONFLICT DO NOTHING`）
4. **参加は1つのトランザクションで、招待のロック（`FOR SHARE`）・メンバーの追加・通知のアウトボックスへの追加を行う**
   - どれか1つだけが起きることを防ぐ（参加したのに通知が予約されない、など）
   - `FOR SHARE` は、同時の取り消し（`UPDATE`）を待たせる。取り消しが先に終われば、参加の側は待ったあとに条件（`revoked_at IS NULL`）で外れ、無効になる
   - 同じ人の参加が同時に届いても、ユニーク制約と `ON CONFLICT DO NOTHING` で1つだけが成功する（結合テストで8件の同時の参加を確認）
5. **招待の確認と参加に、利用者ごとのトークンバケット（10回まで続けて使え、6秒に1回回復する）をかける**
   - 超えたら `429 rate_limited` と `Retry-After`（秒）を返す
   - 招待コードは約8500億通りあり、1分に約10回では総当たりに十数万年かかる
   - `golang.org/x/time/rate` を使う（Google の SDK の依存としてすでに入っていた）。oapi-codegen の strict middleware は operationID を受け取れるので、2つの操作にだけかける
   - しばらく（10分）使われていない利用者の状態は、1分に1回片付ける

## 残る課題
- 制限はインスタンスのメモリで数えるため、Cloud Run のインスタンスが増えると、合計の上限もその数だけ増える。総当たりを防ぐ目的には十分なので、MVP では許容する
- 設計にある IP ごとの制限は、まだかけていない。招待の API は認証が必要で、アカウントは Apple / Google でしか作れないため、まず利用者ごとの制限で十分と判断した。Cloud Run の前段（Cloud Armor など）での制限は、公開の前に検討する
- 参加の通知の送信（アウトボックスからオーナーへ）は、通知のジョブ（タスク 12.x）で作る
