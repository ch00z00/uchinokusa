# 0020. 完了は行ロックの中で予定の回を照らし合わせ、重複には先の記録を返す

- 状態：採用
- 日付：2026-11-05
- 関連：タスク 8.1、`server/internal/domain/care_record.go`、`server/internal/app/care_record.go`、`server/internal/adapter/postgres/care_records.go`、要件10-1〜10-3・10-5・11-2〜11-4
- 前提：設計の判断2（サイクル番号と部分ユニーク制約）、0018、0019

## 決定
1. **完了（`POST /tasks/{id}/completions`）は、1つのトランザクションで行う**
   - タスクの行ロック（`SELECT … FOR UPDATE`）→ 予定の回の照合 → 記録の作成 → タスクの更新 → 完了通知のアウトボックスへの追加
   - 同じタスクへの同時の完了は、行ロックで順番に処理される。後のほうは、先のコミットのあとのタスク（回が進んでいる）を見るので、先に完了した記録を返せる
   - 部分ユニーク制約 `care_records_one_completion_per_cycle_idx` は、最後の砦として残す。ロックを通らない書き込みがあっても、重複の完了は保存されない（このときは詳細なしの `already_completed` になる）
   - 結合テストで、10件の同時の完了のうち1件だけが成功し、残りの9件が「先の記録つきの重複」になることを確かめる。行ロックを外すとこのテストが落ちることも確かめた
2. **照らし合わせの規則は、domain の純粋な関数（`PlanCompletion`）にする**
   | 送った `cycleSeq` | 結果 |
   |---|---|
   | タスクの今の回と同じ | 完了。次回予定 = 実施日 + 実施日の季節の周期。回を1つ進め、`due_overridden` を外す |
   | 今の回より前、`allowExtra` なし | `409 already_completed`。先に完了した記録（誰が・いつ）と最新のタスクを返す |
   | 今の回より前、`allowExtra` あり | 追加の記録（`is_extra`）として保存し、タスクの予定は変えない |
   | 今の回より後 | `409 stale_cycle`（アプリの表示が古い） |
   - 今の回より前でも、その回の完了の記録がない場合（取り消しのあとなど）は `stale_cycle` にする
   - 今の回で `allowExtra` が送られても、通常の完了にする（アプリが再送で付けたままでも、正しく記録されるように）
3. **追加の記録は、タスクの予定を変えない**。その回はすでに完了しており、予定は先の完了で決まっているため。取り消しで戻す先（`prev_next_due_on`・`prev_cycle_seq`）も持たない
4. **実施日を省くと、世帯のタイムゾーンでの今日にする**。過去の日付は受け付け（要件10-3）、その日から次回予定を計算する。未来の日付は `422`（`fields.performedOn = invalid`）にする
   - 設計では「リクエストした人の端末での今日」としていたが、サーバーは端末のタイムゾーンを知らないため、世帯のタイムゾーンにした。アプリが日付を送れば、その日で記録する
5. **一時停止中のタスクも完了でき、一時停止のままにする**（0019 の持ち越し）。止めている間に水やりをした場合も記録を残せるようにするため。再開すると、0019 の規則で次回予定が決まる
6. **完了通知は、追加の記録も含めて、すべての完了をアウトボックスに積む**（要件16-1）。まとめ（要件16-4）と送信は、ジョブ（12.2）が行う
7. 作業の種類・作業名・作業した人の表示名は、記録の時点の値を写して保存する（タスクの削除・メンバーの退出のあとも履歴を表示するため。要件4-7・8-10）

## 残る課題
- 植え替えのタスクの完了で、植え替えの提案を評価し直す処理は、タスク 10.2 でつなぐ
- 完了の変更の通知（リアルタイムの配信）は、タスク 11.x で加える
- 時差の大きい場所から記録した場合の「未来の日付」の判定：リリース後に対応する（`docs/backlog.md`）
