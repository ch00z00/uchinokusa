# 0022. 取り消しは記録を消して記録前の状態に戻し、まとめて完了は1件ずつ記録する

- 状態：採用
- 日付：2026-11-05
- 関連：タスク 8.3、`server/internal/domain/care_record.go`、`server/internal/app/care_record.go`、`server/internal/adapter/postgres/care_records.go`、`server/db/migrations/00005_care_record_prev_due_overridden.sql`、要件10-4・10-9・16-6
- 前提：設計の「取り消しの条件」「まとめて完了」、0020、0021

## 決定

### 取り消し（`POST /records/{id}/undo`）
1. **取り消せるのは、編集者以上で、記録した本人が、記録してから10分以内に、そのタスクの最新の記録に限る**（`domain.CheckUndo`）
   - ほかのメンバーの記録は `403`。10分を過ぎた場合と、あとに記録がある場合は `409 undo_expired`
   - 最新の記録に限るのは、あとの記録が「この記録のあとの予定日・回」を戻す先にしているため。間の記録を消すと、戻す先が食い違う
   - 期限切れと「あとに記録がある」は、アプリにとって「もう取り消せない」という同じ意味なので、1つのコードにまとめた
2. **取り消しは、記録を消し（物理削除）、タスクを記録する前の次回予定・予定の回・予定日を手で変えた印に戻す**
   - 取り消しは「押し間違いをなかったことにする」操作なので、履歴にも残さない
   - 追加の記録は、タスクを変えていないので、記録を消すだけにする
   - まだ送っていない完了通知は `canceled` にする（要件16-6）。送った通知は、送ったままにする
3. **手で変えた印（`due_overridden`）の記録前の値を、`care_records.prev_due_overridden` に保存する**（マイグレーション 00005）
   - 完了は印を外し（0020）、スキップは印を立てる（0021）ので、記録前の値がないと、取り消したときに正しく戻せない
4. **取り消しも、完了・スキップと同じタスクの行ロックを取ってから、最新の記録かを確かめる**
   - ロックの前に確かめると、同時に来た次の回の完了を見落とし、取り消しの「戻す」で進んだ回を上書きしてしまう
   - 結合テストで、別のトランザクションがロックを持っている間に後の記録を入れ、取り消しが `undo_expired` になることを確かめる。ロックを外すと、このテストが落ちることも確かめた
5. 10分は、サーバーの今の時刻（`now`）と、記録の `created_at`（DB の時刻）で比べる

### まとめて完了（`POST /households/{id}/completions:batch`）
6. **世帯の権限を1回確かめたあと、タスクごとに別のトランザクションで、単独の完了と同じ規則で記録する**（要件10-9）
   - 1件の重複・入力の誤り・ほかの世帯のタスクがあっても、ほかのタスクの完了は止めない
   - 全体の結果は `200` で、送った順に、タスクごとの `status`（`completed`・`already_completed`・`failed`）を返す。`already_completed` には単独の完了と同じく「誰が・いつ」と最新のタスクを入れ、`failed` には単独の完了と同じエラーのコードを入れる
   - 内部のエラーは、項目に `internal` とだけ返し、原因はログに残す
7. **1回に送れるのは1〜50件**。空なら `fields.items = required`、超えたら `fields.items = too_many`。今日やることの一覧から選ぶ数としては十分で、1回のリクエストが長く続かないようにするため
8. HTTP のエラーの変換は、項目ごとの結果でも同じコードになるよう、`errorResponse` に切り出した（`writeError` から使う）

## 残る課題
- 取り消しの変更の通知（リアルタイムの配信）は、タスク 11.x で加える
- まとめて完了は1件ずつ順に記録する。件数が多くて遅い場合は、リリース後に見直す
