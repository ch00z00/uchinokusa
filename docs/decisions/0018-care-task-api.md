# 0018. タスクの初回の予定日は既定で今日とし、周期を変えても次回予定日は動かさない

- 状態：採用
- 日付：2026-11-04
- 関連：タスク 7.1、`server/internal/domain/care_task.go`、`server/internal/app/care_task.go`、`server/internal/adapter/postgres/care_tasks.go`、要件8-1〜8-6・8-8・8-10・6-4

## 決定
1. **初回の予定日（`nextDueOn`）を省いたら、世帯のタイムゾーンでの今日にする**
   - 登録したその日に植物の状態を見て、完了かスキップ（「土が湿っている」など）を選べる。「今日 + 周期」にすると、必要な水やりを見逃すことがある
   - 「今日」はサーバーの時刻ではなく、世帯の `time_zone` で決める（UTC で決めると、日本の朝は前日になる）。そのため、`CareTaskService` は現在時刻を返す関数を受け取り、テストでは固定の時刻を渡す
   - 作成と変更で、予定日の項目名を `nextDueOn` にそろえる（作成時は「初回の予定日」の意味）。エラーの `fields` のキーも同じ
2. **周期を変えても、次回予定日は変えない。新しい周期は、次に完了したときから使う**
   - 自動で計算し直すと、「最後に完了した日」がない場合の扱いなど、利用者から見えにくい規則が増える
   - 予定日も変えたいときは、同じ変更のリクエストで `nextDueOn` を送る。アプリの編集画面に、周期と予定日を並べて出す
3. **予定日を手で変えたら `due_overridden` を立て、季節の切り替えのジョブ（12.4）で計算し直す対象から外す**（設計の「次回予定の計算ルール」）
   - 印を外すのは、完了したとき（8.1）にする。完了すれば、次回予定は改めて周期から計算されるため
4. **作業の種類は、あとから変えられない**
   - 記録（`care_records.task_kind`）は記録の時点の種類を持つが、タスクの種類が途中で変わると、履歴とタスクの対応がわかりにくくなる。変えたい場合は、タスクを作り直す
   - 作業名（`customName`）は、種類が「その他」のときだけ使う。ほかの種類で送られても無視する
5. **削除は論理削除（`deleted_at`）にし、記録は残す**（要件8-10）
   - 削除したタスクは、一覧・変更・削除のどれでも見つからないもの（404）として扱う
6. **作成画面の初期値（要件6-4）は、`GET /plants/{id}/task-defaults` で返す**
   - 植物マスタには、出典で確かめた水やりの実行条件だけがあり、推奨周期はない（0009・0015）。そのため、今は水やりの実行条件だけを返す。推奨周期を出典つきで入れられたら、同じ API に項目を追加する
7. **入力の上限**：周期は1以上で、日なら365、週なら52、月なら24まで（植え替えの2年ごとまで）。作業名は20文字、実行条件は100文字、メモは200文字まで
   - 要件に決まりがないため、通知（「〇〇の葉水」）や今日やること一覧の1行に収まる長さにした。メモはスキップの理由と同じ200文字にした
8. **季節ごとの周期の変更は、まるごと置き換える**（`{}` で季節ごとの周期をなくす）
   - 季節ごとに足し引きする API にすると、送る側と受ける側の両方が複雑になる。編集画面は4つの季節をまとめて扱う

## 残る課題
- 植え替えのタスクの予定日を手で変えたときに、植え替えの提案を評価し直す処理（要件17-8）は、タスク 10.2 でつなぐ
- タスクの変更の通知（リアルタイムの配信）は、タスク 11.x で加える
- アーカイブした植物にもタスクを作れる：リリース後に対応する（`docs/backlog.md`）
