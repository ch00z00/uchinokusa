# 0012. 世帯のオーナーは常に1人とし、移譲はトランザクションの中で行をロックして行う

- 状態：採用
- 日付：2026-11-02
- 関連：タスク 4.3、`server/internal/app/membership.go`、`server/internal/adapter/postgres/members.go`、要件2-7・2-8・4-6〜4-8

## 背景
- 要件には「唯一のオーナーは、ほかにメンバーがいる限り退出できない」（2-8）とあるが、オーナーが何人いてよいかは決まっていなかった
- オーナーを複数にすると、「最後のオーナーかどうか」を、退出・ロールの変更・削除・アカウントの削除のたびに、同時の操作も考えて数える必要がある

## 決定
1. **オーナーは常にちょうど1人とする**
   - ロールの変更では `owner` を指定できない（`fields.role = invalid`）。オーナーの交代は移譲だけで行う
   - オーナーは、自分のロールを変えられず、退出もできない（`409 last_owner`）
2. **オーナーが自分だけの世帯では、退出ではなく世帯の削除をしてもらう**
   - 退出したときに世帯を自動で消すと、確認なしにデータが消える。世帯の削除には、アプリでの確認がある（要件2-6）
   - ほかにメンバーがいる場合は、先に移譲してもらう（要件2-8）
3. **移譲はトランザクションの中で、元のオーナーと移す先の2行を `SELECT ... FOR UPDATE` でロックしてから行う**
   - ロックしないと、同じオーナーが複数の人への移譲を同時に送ったときに、オーナーが複数になる。ロックを外して試したところ、8件の同時の移譲でオーナーが3人になった
   - ロックすると、2つ目以降の移譲は待ち、待ったあとに読み直した元のオーナーはもう編集者なので、403 になる
   - 2行は ID の順にロックする。トランザクションごとに順番が違うと、互いに相手の行を待ち合うデッドロックが起きうる
   - トランザクションは、今はリポジトリのメソッドの中に閉じる（`pgx.BeginFunc`）。複数のリポジトリにまたがるトランザクションが必要になったら、仕組みを見直す
4. **移す先がメンバーでない場合は 422（`fields.userId = not_member`）にする**
   - 世帯にはアクセスできているので、存在を隠す 404 ではなく、入力の誤りとして返す
5. **外したメンバーの記録は、何もしなくても残る**
   - 記録の作業者は `users` を参照し、作業者名を記録の行に持つ。`memberships` は参照しないので、メンバーシップを消しても記録は消えない（要件4-7・12-5）

## 残る課題
- ロールの変更・メンバーの削除では、`Authorizer` でオーナーであることを確かめてから、別の文で更新する。そのあいだに移譲が終わると、元のオーナーの操作が1回だけ通りうる。影響が小さいため、MVP では許容する
- ロールの変更・削除を、そのメンバーの端末にすぐに知らせる処理（要件4-6・4-7）は、リアルタイム同期のタスク 11.x で加える。API のアクセスは、毎回 DB のメンバーシップを確かめるため、すぐに止まる
