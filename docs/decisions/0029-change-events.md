# 0029. 変更イベントは書き込みと同じトランザクションの最後に発行し、pg_notify でインスタンス間に配る

- 状態：採用
- 日付：2026-11-06
- 関連：タスク 11.1、`server/internal/adapter/postgres/changes.go`、`server/internal/domain/change.go`、`server/internal/app/actor.go`、`server/db/queries/changes.sql`、要件11-1
- 前提：設計の ChangeBroadcaster と RealtimeHub、「イベントの取り決め」

## 決定
1. **世帯のデータを変える書き込みは、すべて `withChanges` のトランザクションで行い、集めた変更イベントをコミットの直前に発行する**（設計どおり、アプリの層で発行する）
   - 発行は、イベントごとに「世帯のバージョン番号を1つ進める（`UPDATE households SET version = version + 1 RETURNING version`）→ `pg_notify('household_changes', JSON)`」
   - `pg_notify` の通知は、PostgreSQL の仕様で**コミットしたときにだけ**届き、ロールバックすれば届かない。そのため「確定したあと」に知らせることになり、失敗した書き込みのイベントは出ない
   - バージョン番号を進めるのは、トランザクションの最後にする。世帯の行のロックをいつもいちばん後に取るので、タスクや提案の行ロックとの順序が食い違わず、デッドロックが起きない
   - 世帯の削除だけは、行を消すとバージョンを進められないので、消す前に発行する（届くのはコミットしたあと）
   - 1文で済んでいた書き込み（植物・置き場所・メモ・タスクの変更など）も、トランザクションにした。1件の書き込みにつき、バージョンの更新と通知の2文が増える
2. **データベースのトリガーでは発行しない**
   - トリガーなら書き込みの出し忘れが起きないが、「誰が変えたか」がわからない。植物の削除のように連鎖して消えるデータでは、子の行の数だけイベントが出てしまう
   - 出し忘れは、すべての書き込みについて、出るイベントを並べた結合テスト（`TestChanges_EveryWrite`）で防ぐ。書き込みを足したら、このテストにも足す
3. **イベントは「何が変わったか」だけを持つ**：世帯・バージョン・データの種類・ID・操作（created / updated / deleted）・操作した人・植物（植物に属するデータのとき）
   - データそのものは入れない。通知の中身は 8000 バイトまでで、アプリは受け取ったら取り直すため
   - 項目の名前は、アプリに送るメッセージ（設計の RealtimeMessage）にそろえる。11.2 でそのまま転送できるようにするため
4. **1つの操作で変わったデータごとに、イベントを出す**
   | 操作 | イベント |
   |---|---|
   | 完了・スキップ | 記録の created と、タスクの updated（追加の記録はタスクを変えないので、記録だけ） |
   | 取り消し | タスクの updated（戻した場合）と、記録の deleted |
   | 記録の編集・削除 | 記録の updated / deleted と、次回予定を計算し直したときだけタスクの updated |
   | 提案の採用 | タスクの created（タスクを作る提案のとき）と、提案の updated |
   | 提案の撤回（0028） | 撤回した提案ごとに updated |
   | 撤回した提案を未回答に戻す | 提案の created（アプリには、新しく現れた提案のため） |
   | オーナー権限の移譲 | 2人のメンバーの updated |
   | 表示名の変更 | 所属するすべての世帯に、メンバーの updated |
   - 連鎖して変わるデータ（植物の削除で消えるタスク・記録・メモ・提案、置き場所の削除で「置き場所未設定」になる植物）は、親のイベント1件だけにする。アプリは親のイベントから、関係するデータを取り直す
   - 何も変えなかった操作（完了済みの回への重複、同じキーの提案の保存）は、イベントを出さない
   - 通知設定（自分だけの設定）と招待の作成・取り消しは、ほかのメンバーの画面に出ないので、イベントを出さない
5. **操作した人は、認証の middleware が context に入れ（`app.WithActor`）、発行するときに読む（`app.ActorFrom`）**
   - すべてのリポジトリの引数に足さずに済むようにするため。ジョブなど人の操作でない書き込みでは、項目がない
6. **受け取りは `ChangeListener` が、プールから切り離した専用の接続で `LISTEN` して行う**
   - どの API インスタンスで起きた変更も、すべてのインスタンスが受け取れる（Cloud Run で複数のインスタンスが動いても届く）
   - 接続が切れたら、待つ時間を 1秒から倍にしながら（最大30秒）つなぎ直す。切れている間の通知は失われる。配信は「最大1回」で、アプリは再接続とバージョン番号の飛びで取り直す（設計どおり）
   - 読めない通知は、ログに残して飛ばす
   - 11.1 の時点では、受け取ったイベントをログに残すだけ。WebSocket への配信は 11.2 でつなぐ

## 残る課題
- WebSocket での購読と配信（11.2）
- バージョン番号の更新で、世帯の書き込みが世帯の行のロックで順番になる。家族の人数では問題にならないが、書き込みの多い世帯で遅くなるようなら見直す
