# 0025. メモの編集・削除は作成者本人かオーナーに限り、本文が変わったときだけ編集済みにする

- 状態：採用
- 日付：2026-11-05
- 関連：タスク 9.2、`server/internal/domain/note.go`、`server/internal/app/note.go`、`server/internal/adapter/postgres/notes.go`、`server/db/queries/notes.sql`、要件13-1〜13-5
- 前提：設計の権限の表（`note.write` と `CanModifyNote`）、0023

## 決定
1. **エンドポイントは `GET`・`POST /plants/{id}/notes` と、`PATCH`・`DELETE /notes/{id}`**（設計どおり）
   - 一覧は閲覧者も見られる。作成は編集者以上（`note.write`）
   - 編集・削除は、`note.write` を持ち、かつ作成者本人かオーナーであること（`domain.Membership.CanModifyNote`、要件13-3）。作成者が退会したメモは、オーナーだけが扱える
   - 確かめる順番は、メンバーか（404）→ ロール（403）→ 作成者本人か（403）→ 入力（422）。権限のない人に、入力の誤りを先に見せない
   - 作成者はあとから変わらないので、作成者を確かめてから書き換えるまでの間に、ロックは取らない
2. **本文は前後の空白を除いてから検証し、空なら `fields.body = required`、2000文字を超えれば `fields.body = too_long`**（要件13-4）
   - 文字数はバイト数ではなく文字で数える。データベースの CHECK 制約（`char_length(body) BETWEEN 1 AND 2000`）と同じ数え方にする
   - 設計のエラーの表には `note_too_long` というコードの例があるが、ほかの入力欄と同じく `validation_failed` の `fields` で返す。アプリが入力欄ごとにエラーを出す処理を、1つにまとめられるため
3. **編集した日時（`editedAt`）は、本文が変わったときだけ付ける**
   - 同じ本文で保存しただけで「編集済み」と表示されないようにするため。判定は UPDATE の中で行う（`CASE WHEN body = 新しい本文 THEN edited_at ELSE now() END`）
4. **一覧は作成日時・ID の新しい順にし、履歴（0023）と同じ形のカーソルでページに分ける**（既定30件、最大100件）
   - 編集しても並びは変えない。並びが変わると、アプリでメモを探しにくくなるため
   - 作成日時が同じメモは、ID の順で並べる。カーソルに ID を含めて、ページの境目で抜けや重なりが出ないようにする
5. **作成者の名前は、作成の時点の値を写して持つ**（記録と同じ。0020）。アカウントを削除すると作成者の ID は NULL になり、名前は残る
6. アーカイブした植物にもメモを書ける。アーカイブした植物でも、記録とメモは見られるようにする（要件5-8）ため、書くことも止めない
7. 画像の添付は扱わない（要件13-5）

## 残る課題
- メモの変更を、ほかのメンバーの画面に配信する処理（要件11-1）は、タスク 11.x で加える
- アカウントの削除で、作成者の名前を「退会したユーザー」にする処理は、アカウントの削除のタスクで行う
