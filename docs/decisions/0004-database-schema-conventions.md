# 0004. DB のスキーマの取り決め（複合外部キー、text + CHECK、UUIDv7、テストごとのデータベース）

- 状態：採用
- 日付：2026-10-26
- 関連：タスク 1.3、`server/db/migrations/00001_init.sql`、design.md「物理データモデル」、要件20-2・11-4・19-8

## 背景
設計書でテーブルと主な制約は決まっていた。ただし、次の点は、マイグレーションを書く段階で決める必要があった。
1. 「植物・タスク・記録は、世帯をまたいで参照しない」という不変条件を、どこで保証するか
2. 列挙値（ロール、作業の種類など）を、どの型で表すか
3. UUIDv7 の主キーを、どこで作るか（PostgreSQL 16 には生成する関数がない）
4. 結合テストで、テストどうしのデータが混ざらないようにする方法

## 決定と理由
### 1. 世帯の配下の外部キーは `(id, household_id)` の組で張る
```sql
FOREIGN KEY (plant_id, household_id) REFERENCES plants (id, household_id) ON DELETE CASCADE
```
- 単純な `plant_id → plants(id)` だと、`household_id = 世帯A` の行に、世帯Bの植物の `plant_id` を入れられてしまう
- 組で張ると、「参照先の植物も同じ世帯にある」ことを DB が保証する。アプリのクエリに不具合があっても、別の世帯のデータとつながった行はできない（要件20-2 の最後の砦）
- 置き場所の削除は `ON DELETE SET NULL (location_id)` とし、列を指定して `household_id` は残す（PostgreSQL 15 以降の構文）
- トレードオフ：親のテーブルに `UNIQUE (id, household_id)` が要る（主キーと重複するインデックスが1つ増える）

### 2. 列挙値は `text` + `CHECK` 制約で表す
- PostgreSQL の `ENUM` 型は、値の追加はできるが、削除・並べ替えができず、トランザクションの中で追加した値をすぐに使えない、などの制約がある
- `CHECK` なら、値の変更が制約の付け替えだけで済む。API は「列挙値の追加だけを許可する」（要件19-9）ため、DB も追加しやすい形にそろえる

### 3. UUIDv7 は DB の関数（`uuid_generate_v7()`）を列の初期値にする
- アプリが ID を渡さなくても、DB が作る。SQL を直接書くテストやデータの投入でも、ID の形式がそろう
- アプリ（Go の `uuid.NewV7()`）から ID を渡すこともできる
- PostgreSQL 18 で標準の `uuidv7()` が使えるようになったら、置き換える

### 4. 結合テストは、マイグレーション済みのテンプレートからデータベースを複製する
- コンテナはテストのパッケージごとに1つだけ起動し、テストごとに `CREATE DATABASE ... TEMPLATE` で新しいデータベースを作る（数十ミリ秒）
- テストを `t.Parallel()` で並行に実行しても、互いのデータが見えない。テストの後片付け（TRUNCATE など）も要らない

### その他
- `updated_at` は、トリガー（`set_updated_at`）で自動的に更新する。クエリで書き忘れても正しくなる
- マイグレーションの SQL は `embed` でバイナリに埋め込み、`uchinokusa migrate` で goose をライブラリとして実行する。本番のコンテナに SQL ファイルや goose の CLI を置かなくてよい
- 植物マスタの検索インデックス（`pg_trgm`）は、検索のクエリとあわせてタスク 6.1 で作る

## 見直す条件
- PostgreSQL 18 以降に上げたとき（UUIDv7 の関数）
- 世帯をまたいだデータの移動（植物を別の世帯に移す、など）が必要になったとき
