# 0015. 植物マスタは出典のない値を仕組みで拒否し、検索は正規化した文字列の部分一致で行う

- 状態：採用
- 日付：2026-11-03
- 関連：タスク 6.1、`server/db/seeds/species.yaml`、`server/internal/domain/species.go`、`server/internal/adapter/seedfile/`、要件6-1・6-2・6-5・6-6・17-10

## 背景
- 植え替えの時期の既定値を、出典を確かめずに置いてしまったことがあった（docs/decisions/0009）。植物マスタの値は量が多いので、人の注意だけに頼らず、仕組みで防ぎたい
- 30〜50種すべての性質を調べるのは時間がかかる。ユーザーと相談し、名前は全種、性質は主要な10種を出典つきで入れ、残りは名前だけにすることにした

## 決定
1. **初期データは `db/seeds/species.yaml` に書き、性質の値には項目ごとに出典を書く**
   - 出典には URL・題名・確認日・その出典にもとづく項目（`fields`）・根拠の文（`quote`）を書く
   - 値を入れた項目が、どの出典の `fields` にもない場合と、出典の `fields` に挙げた項目に値がない場合は、検証のエラーにする。`seed` は検証に通らなければ何も投入せず、リポジトリの初期データそのものを検証するテストもある
   - YAML の知らない項目（書き間違い）もエラーにする。無視すると、出典の検証をすり抜けるため
   - わからない値は空（DB では NULL）にし、推測で埋めない
2. **出典は、NHK出版「みんなの趣味の園芸」の植物図鑑を主にする**
   - 出版社の図鑑で、植物ごとに日当たり・水やり・植え替えの適期が書かれている。最低温度の数値は一部の種類にしか書かれていないので、書かれていない種類は空にした
   - 出典の文から値への決め方（例：「日当たりのよい場所」→ `light_level: high`）は、YAML の先頭に書いた
3. **種類ごとの植え替えのルールは、適期だけを種類ごとに上書きし、避ける時期は既定値から適期の月を除いたものにする**
   - 図鑑には「適期」は書かれていても「避ける時期」は書かれていないため。例：適期が5〜9月のモンステラは、7〜8月が適期になり、避ける時期は12〜2月になる
   - 「5月中旬から」のように月の途中から始まる場合も、月の単位で扱うため、その月を含めた
4. **投入は `slug`（例：`monstera-deliciosa`）をキーにした追加・上書きで行い、ファイルから消えた種類は削除しない**
   - 何度実行しても同じ結果になる。植物から参照されている種類を消さないため
5. **検索は、正規化した文字列（`search_text`）の部分一致（`LIKE '%…%'`）で行う**
   - 正規化：全角・半角（NFKC）、大文字・小文字、ひらがな・カタカナをそろえ、空白と中黒を除く。SQL では書きにくいので、投入のときにアプリで作って列に保存する
   - 和名・学名・別名を空白で区切ってつなぐ。検索語からは空白を除くので、名前をまたいで一致しない
   - 一致した位置が前（和名）のものほど先に並べる。検索語の `%` と `_` はエスケープする
   - `pg_trgm` の GIN 索引で部分一致を速くする。ただし、数十件のデータでは効果はほとんどなく、データが増えたときの備えである
   - 誤字を許す本当の「あいまい検索」（類似度での検索）は、必要になったら `pg_trgm` の `similarity` で加える
6. **sqlc で、NULL になりうる `numeric` を `*float64`、`boolean` を `*bool` にする**（既定は pgtype の型）

## 残る課題
- 名前だけの24種の性質を、出典を確かめながら足す（推奨の水やりの周期の数値は、図鑑にも書かれていないことが多い。周期はユーザーが決める前提とし、条件の文だけを初期値にする）
- 名前の表記（学名を含む）は出典で確かめていない。分類の変更（サンセベリアがドラセナ属に移った、など）は、図鑑の表記に合わせた
