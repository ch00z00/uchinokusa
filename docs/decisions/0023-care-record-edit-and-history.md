# 0023. 記録の編集・削除で次回予定を計算し直すのは、予定を決めた最新の完了に限る

- 状態：採用
- 日付：2026-11-05
- 関連：タスク 8.4、`server/internal/domain/care_record_history.go`、`server/internal/app/care_record.go`、`server/internal/adapter/postgres/care_record_history.go`、要件12-1〜12-5
- 前提：設計の「編集・削除」、0020、0021、0022

## 決定

### 記録の編集（`PATCH /records/{id}`）・削除（`DELETE /records/{id}`）
1. **編集者以上なら、記録した本人でなくても、実施日の編集と削除ができる**（要件12-4）。編集できるのは実施日だけ（未来の日付は `422`）。取り消し（0022）と違い、時間の制限はない
2. **次回予定を計算し直すのは、次のすべてを満たす場合だけにする**（`domain.RescheduleAfterChange`）
   - 変えた記録が完了である（スキップは予定の起点にならない）
   - 変えた記録が、変更の前か後で、タスクの最新の完了（実施日の新しい順）である
   - タスクの予定を最後に決めた記録（追加の記録を除き、記録した順で最後のもの）が完了である。あとにスキップがあれば、ユーザーが選んだ確認日を残す
   - 変更のあとに、完了が残っている
3. **計算し直すときは、変更のあとの最新の完了の実施日から「実施日 + 実施日の季節の周期」にし、手で変えた印を外す**（完了と同じ規則、0020）
   - 手で変えた予定日のあとに最新の完了を編集した場合も、周期からの計算に戻す。完了の実施日を直すのは、予定の起点を直すことだから
   - 予定の回は変えない（削除でも戻さない）。回は「完了するたびに進む番号」で、古い回をもう一度開くと、重複の防止（0020）の前提が崩れるため
4. **完了がすべてなくなる削除では、次回予定を変えない**。計算の起点がないため（`docs/backlog.md`）
5. 削除した記録の、まだ送っていない完了通知は送らない（要件16-6、0022 と同じ）
6. 編集・削除も、完了・スキップ・取り消しと同じタスクの行ロックの中で行う。タスクを削除していれば、記録だけを変える（API ではタスクの項目を省く）

### 履歴（`GET /plants/{id}/records`）
7. **記録を、実施日 → 記録した日時 → ID の新しい順に返す**（要件12-1）。同じ実施日の記録も、順番が決まる
8. **ページ送りは cursor 方式にする**。cursor は、前のページの最後の記録の「実施日・記録した日時・ID」を符号化した文字列で、アプリは中身を解釈せずに送り返す
   - 件数（offset）方式と違い、ページを読む間に記録が増えても、重複や抜けが起きない
   - 1ページは既定30件、最大100件
9. **`kind` で絞り込める**（要件12-2）。値は作業の種類（`CareKind`）で、ほかの値は `422`
10. **種類ごとの最終実施日（`lastPerformed`）を、同じレスポンスで返す**（要件12-3）
    - `other` は作業名ごとに分ける（「葉水」と「株の回転」は別の作業のため）
    - スキップは実施に数えない
    - `kind` の絞り込みにかかわらず、すべての種類を返す（画面の上部に、つねに全体の最終実施日を出すため）
11. 閲覧者も見られる。世帯を抜けたメンバーの記録も、記録の時点の名前で返す（要件12-5。記録に名前を写して持つ、0020）

## 残る課題
- 完了をすべて消したときの次回予定：リリース後に対応する（`docs/backlog.md`）
- 記録の変更の通知（リアルタイムの配信）は、タスク 11.x で加える
