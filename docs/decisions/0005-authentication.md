# 0005. 認証は生成したルーティングのミドルウェアで行い、ユーザーは初回のアクセスで作る

- 状態：採用
- 日付：2026-10-29
- 関連：タスク 2.1、`server/internal/adapter/httpapi/auth.go`、`server/internal/adapter/firebase/`、要件1-2・1-3

## 決定
1. **認証は、oapi-codegen の `StdHTTPServerOptions.Middlewares` で、`/v1` のすべてのエンドポイントにかける**
   - エンドポイントを追加しても、認証のかけ忘れが起きない。`/healthz` は対象外にする
   - API 定義にも、全体の `security`（`firebaseIdToken`）として書く
2. **ユーザーは、初めてのアクセスで作る（「まず読み、なければ作る」）**
   - ほとんどのリクエストは既存のユーザーなので、まず `SELECT` だけを行う。毎回の書き込み（`INSERT ... ON CONFLICT DO UPDATE`）を避ける
   - 作るときは `ON CONFLICT DO NOTHING` にし、行が返らなければ読み直す。同時に届いた初回のリクエストでも、ユーザーは1人だけになる
   - 削除済みのユーザーは、トークンがまだ有効でも 401 にする
3. **表示名は、前後の空白を除いて1〜30文字**
   - 要件に長さの決まりがないため、通知の文面やメンバーの一覧に収まる長さにした
   - 初期値（プロバイダの名前）は、エラーにせず30文字に切り詰める。Apple は ID トークンに名前を含めないため、空のこともある（アプリで設定を促す）
4. **トークンの検証のテストは、Firebase Auth Emulator を testcontainers で起動して行う**
   - `dev/firebase-emulator` の Dockerfile をそのまま使い、イメージを残して2回目以降の起動を速くする
   - Emulator は署名を確かめないため、期限切れ・別のプロジェクト向けのトークンを自作して確かめる。想定どおりの理由で拒否されたかを、エラーの文言でも確かめる

## 補足
- 公開鍵を取得できない（Google への接続の障害）場合は、トークンの問題ではないため、401 ではなく 500 にする
- トークンの失効の確認（`VerifyIDTokenAndCheckRevoked`）は、リクエストごとに Firebase への問い合わせが増えるため、MVP では行わない。アカウントの削除（タスク 13.1）では DB の `deleted_at` で止める
