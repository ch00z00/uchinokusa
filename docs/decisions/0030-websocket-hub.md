# 0030. WebSocket は Authorization ヘッダーで認証し、購読と配信を1つずつ順に行う

- 状態：採用
- 日付：2026-11-07
- 関連：タスク 11.2、`server/internal/adapter/ws/`、`server/internal/adapter/httpapi/router.go`、`server/cmd/uchinokusa/main.go`、要件11-1・4-6・4-7・20-1
- 前提：0029（変更イベントの発行と pg_notify）、設計の RealtimeHub と「イベントの取り決め」

## 決定
1. **接続は `GET /v1/ws` で、ほかの API と同じ `Authorization: Bearer <ID トークン>` で認証する**
   - 設計では `?token=` も挙げていたが、使わない。Cloud Run のリクエストのログには URL のクエリが残るため、トークンがログに残ってしまう
   - React Native の WebSocket は、接続するときにヘッダーを付けられる。付けられないとわかったら、最初のメッセージでトークンを送る形を足す
   - WebSocket は OpenAPI では表せないので、API 定義には入れず、ルーターで直接登録する
   - 1本の接続は、最大1時間（ID トークンの有効期限）で閉じ、つなぎ直させる。Cloud Run のタイムアウトの設定に頼らずに、期限の切れたトークンで接続し続けないようにする
2. **メッセージの取り決め**（設計の RealtimeMessage に、`subscribed` を足した）

   | 向き | メッセージ | 意味 |
   |---|---|---|
   | アプリ → サーバー | `{"type":"subscribe","householdIds":[...]}` | 購読する世帯を、この一覧に置き換える（最大50世帯） |
   | アプリ → サーバー | `{"type":"ping"}` | 生存の確認。React Native からは WebSocket の ping を送れないため |
   | サーバー → アプリ | `{"type":"subscribed","householdIds":[...]}` | 所属を確かめて購読した世帯。アプリは、これを受け取ってからデータを取り直す（取り直しと購読の間の変更を逃さないため） |
   | サーバー → アプリ | `{"type":"changed", ...}` | 変更イベント。項目は 0029 の通知と同じ。`actorUserId`・`plantId` は、ないときは入れない（ジョブの書き込みには操作した人がいない） |
   | サーバー → アプリ | `{"type":"membership_revoked","householdId":...}` | 所属していない（外された）世帯。購読から外す。購読を求めた世帯に所属していないときも送る |
   | サーバー → アプリ | `{"type":"role_changed","householdId":...,"role":...}` | ロールが変わった |
   | サーバー → アプリ | `{"type":"pong"}` | `ping` への応答 |

   - 読めないメッセージや、多すぎる世帯の購読は、接続を閉じる（1008）。知らない種類のメッセージは、新しいアプリとの組み合わせのために無視する
3. **変更イベントは、その世帯を購読しているすべての接続に送る。操作した人の接続にも送る**
   - アプリはバージョン番号を抜けなく追って取りこぼしを見つける（0029）ので、自分の変更のイベントも要る。同じ人のほかの端末にも届く
4. **メンバーの変更のイベントでは、変更を受けた本人の接続の購読を見直す**（要件4-6、4-7）
   - 削除なら、`membership_revoked` を送って購読から外し、その削除のイベントは送らない
   - 更新なら、所属とロールを確かめ直す。所属がなければ削除と同じにし、ロールが変わっていれば `role_changed` を送る（表示名の変更など、ロールが変わらなければ送らない）
   - 世帯の削除のイベントは、送ったあとで、その世帯の購読をすべてやめる
5. **購読の確認（`subscribe`）とイベントの配信（`Publish`）は、1つずつ順に行う**
   - 所属を確かめてから購読に入れるまでの間に、そのメンバーの削除のイベントを配ってしまうと、削除されたメンバーが購読したまま残る。順に行えば、削除は購読に入れたあとで配られ、外せる
   - 確かめるのは DB の問い合わせ（数件）なので、家族の規模では待ちは問題にならない
6. **取りこぼしたかもしれないときは、接続を閉じて、つなぎ直させる**
   - アプリはつなぎ直すと、購読し直し（所属を確かめ直す）、データを取り直す（要件11-5）。1つの仕組みで、変更とメンバーの変更の取りこぼしの両方から回復できる
   - 変更イベントの受け取り（ChangeListener）が LISTEN をつなぎ直したとき（`OnListen` で `Hub.Reset`）。切れていた間のイベントは失われているため。起動の直後に LISTEN を始める前の接続も、これで購読し直させる
   - 送り待ちがあふれた（アプリが受け取りきれていない）接続は、閉じる手続きをせずに切る
   - 閉じる理由は、つなぎ直してよいものを 1013（Try Again Later）、保つ時間の経過とサーバーの停止を 1001（Going Away）にする
7. **30秒ごとに ping を送り、10秒以内に応答がなければ、接続を切る**
   - サーバーを止めるときは、`http.Server.Shutdown` が WebSocket に切り替えた接続を待たないので、その前に `Hub.Shutdown` ですべての接続を閉じ、ほかのインスタンスへつなぎ直させる

## 残る課題
- ID トークンの有効期限は見ず、接続から1時間で閉じる。トークンの残りの時間に合わせて閉じるのは、必要になったら（トークンの検証で期限を返す）
- アプリの側（再接続・バージョン番号の追跡・クエリの無効化）は、タスク 18.1 で作る
