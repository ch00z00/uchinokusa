# 0001. API の定義を `api/` ディレクトリに YAML で置く

- 状態：採用
- 日付：2026-10-24
- 関連：`.kiro/specs/household-plant-care-mvp/design.md`（技術スタック、API の取り決め）、要件19-9

## 背景
uchinokusa は「API の定義を先に書く」方式を採る。1つの OpenAPI の定義から、次の2つを自動で生成する。

```
            api/openapi.yaml（唯一の正）
               │                   │
     oapi-codegen で生成     openapi-typescript で生成
               ▼                   ▼
   server/：Go のハンドラーの型   mobile/：TypeScript の型
```

このため、定義ファイルはサーバーにもアプリにも属さない「両者の約束事」である。モノレポの中で、これをどこに、どの形式で置くかを決める必要があった。

## 検討した案
| 案 | 内容 | 評価 |
|---|---|---|
| A | `server/api/openapi.yaml`（サーバーの中に置く） | 個人開発の規模なら困らない。ただしアプリがサーバーのディレクトリに依存する形になり、「サーバーの都合で API を変える」流れになりやすい |
| B | ルートに `openapi.json` を1ファイルで置く | 技術的には問題ない（生成ツールはパスを指定するだけ）。ただし、定義の分割や関連ファイルの置き場所がなく、ルートも散らかる。JSON はコメントを書けない |
| C | `api/openapi.yaml`（専用のディレクトリに YAML で置く） | 採用 |

## 決定
API の定義は、**ルート直下の `api/` ディレクトリ**に、**YAML 形式**で置く。入口のファイルは `api/openapi.yaml` とする。

## 理由
1. **依存の向きがはっきりする**：サーバーとアプリが、同じ1つの定義に対等に依存する形になる
2. **「先に約束を決める」流れを守りやすい**：機能の追加は「① `api/` を変える → ② 両方の型を生成し直す → ③ それぞれ実装する」の順になる。約束の変更が、独立した差分としてレビューで見える
3. **互換性のチェックの対象を絞れる**：「項目の追加だけを許可する」ルール（要件19-9）を将来 CI で確認するとき、`api/` だけを対象にすればよい
4. **大きくなったら分割できる**：MVPでもエンドポイントは約40あり、1ファイルでは数千行になる見込み。ディレクトリがあれば、パスを変えずに `$ref` で分割できる
   ```
   api/
   ├── openapi.yaml        入口（パスの一覧）
   ├── paths/plants.yaml
   ├── paths/tasks.yaml
   └── schemas/care-record.yaml
   ```
5. **関連ファイルの置き場所になる**：lint（Spectral など）の設定、エラーコードの一覧などを定義のそばに置ける
6. **YAML の方が手書きに向いている**：コメントを書ける（「この項目は要件17-8のため」など）。括弧や引用符が少なく、差分も読みやすい。JSON は、コードから定義を自動生成する方式（定義を後から作る方式）のほうが向いている

## トレードオフ
- 個人開発の規模に対しては、ディレクトリが1つ増えるぶん少しだけ大げさになる
- 当面は `api/openapi.yaml` の1ファイルで始め、分割は必要になってから行う

## 見直す条件
- API の利用者がサーバーとアプリ以外に増えたとき（Web 版、外部公開など）
- 定義をコードから生成する方式に切り替えるとき
