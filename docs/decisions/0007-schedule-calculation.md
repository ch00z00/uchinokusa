# 0007. 次回予定の計算は civil.Date の値の型とメソッドで作り、月の足し算は自前で月末に丸める

- 状態：採用
- 日付：2026-10-31
- 関連：タスク 3.1、`server/internal/domain/schedule.go`、要件8-6・10-2・10-3・10-5

## 決定
1. **日付は `cloud.google.com/go/civil` の `civil.Date` で扱う**
   - 「暦の日付」（タイムゾーンを持たない年月日）を表す型で、`time.Time` の時刻・タイムゾーンによる1日のずれを避けられる
   - Firebase の SDK の依存としてすでに入っていたため、新しく増える依存はない（`go.mod` では直接の依存に変わった）
2. **月の足し算は `civil.Date.AddMonths` を使わず、自前で月末に丸める**
   - `AddMonths` は `time.AddDate` に任せており、1/31 + 1か月 = 3/3 のように繰り上がる。要件では 2/28（うるう年は 2/29）にしたい
   - 1日に揃えてから月を足し、日を `min(元の日, その月の日数)` にする
3. **設計の `ScheduleCalculator` インターフェースは作らず、`Schedule`（基本の周期と季節ごとの周期）のメソッドにする**
   - 状態を持たない純粋な計算なので、差し替えの必要がない。4つの引数を毎回渡すより、周期の組をひとまとめにした型のほうが、呼ぶ側が読みやすい
   - 呼び方：`schedule.NextDueAfterCompletion(performedOn, hemisphere)`
4. **次回予定は、必ず実施日より後にする**
   - 周期の検証はタスクの作成時（タスク 7.1）に行う。それでも不正な周期（0 以下、知らない単位）が来た場合は、実施日の翌日にする
   - 定期ジョブなどをパニックで止めず、同じ日に何度も「やること」に出る状態も避けるため

## 補足
- 季節は、実施日の季節で決める。冬の最終日（2/28）に実施したら、次回予定が春に入っても冬の周期を使う。季節が変わったときの計算し直しは、季節の切り替えのジョブ（タスク 12.4）で行う
- 南半球は、月を6か月ずらしてから北半球と同じ判定をする
