# 0017. 植物の種類はマスタか自由入力の片方だけとし、種類・置き場所の存在は DB の外部キーで確かめる

- 状態：採用
- 日付：2026-11-04
- 関連：タスク 6.3、`server/internal/domain/plant.go`、`server/internal/app/plant.go`、`server/internal/adapter/postgres/plants.go`、`server/db/migrations/00004_plant_search.sql`、要件5-1〜5-8・6-3

## 決定
1. **種類は、植物マスタの ID（`speciesId`）か自由入力（`speciesFreeText`）のどちらか一方だけを持つ**
   - 両方を送ったら 422（`fields.speciesFreeText = exclusive`）。DB にも CHECK 制約（`plants_species_one_of_check`）を入れる
   - どちらを表示すればよいかが曖昧になるのを避けるため。マスタにない種類だけが自由入力になる（要件6-3）
   - 変更（PATCH）では、どちらかの項目を送ると、種類をまるごと置き換える（マスタに替えると自由入力は消え、その逆も同じ）
2. **種類・置き場所が存在しない場合は、DB の外部キーの違反を 422（`invalid`）に変換する**
   - 置き場所の外部キーは `(location_id, household_id)` なので、ほかの世帯の置き場所も同じく拒否できる
   - アプリで先に存在を確かめると、確かめてから保存するまでに消される場合がある。DB の制約なら確実で、クエリも1回で済む
   - 違反した制約の名前（`plants_species_id_fkey`、`plants_location_id_household_id_fkey`）で、どの項目の誤りかを決める
3. **リクエストの ID と日付は、UUID・日付の型ではなく文字列で受け取る**
   - 変更で空文字を「未設定に戻す」の意味に使うため（0011・0016 と同じ）。形式の誤りは 400 ではなく 422（`invalid`）になる
   - 一覧の `locationId` の絞り込み（クエリパラメーター）は、空にする必要がないので UUID の型にする（誤りは 400）
4. **名前の検索は、植物マスタと同じ正規化（`NormalizeSearchText`）を使い、正規化した名前を `name_search` 列に持つ**
   - 部分一致の索引（pg_trgm）は作らない。世帯の植物は多くても数百で、世帯の条件の索引で十分に絞れる
5. **一覧の「次のお手入れ予定日」（`nextDueOn`）は、有効なタスク（一時停止・削除したものを除く）の `next_due_on` の最小値**
   - タスクを作るのはタスク 7.1 なので、それまでは常に項目がない
6. **アーカイブは、`archived_at` を立てるだけで、タスクや記録には触れない**
   - 一覧（`GET /households/{id}/plants`）は、既定でアーカイブした植物を除く。`archived=true` で、アーカイブした植物だけを返す
   - 詳細（`GET /plants/{id}`）は、アーカイブした植物も返す（記録とメモを閲覧するため。要件5-8）
   - アーカイブし直しても、最初にアーカイブした日時を残す。誤った操作を戻せるよう、`/unarchive` も用意する
   - 今日やること・リマインダー（タスク 9.1・12.3）では、アーカイブした植物のタスクを除く
7. **入力の上限**：植物の名前は前後の空白を除いて1〜40文字、自由入力の種類は50文字まで、名前の検索語は100文字まで
   - 要件に決まりがないため、一覧や通知（「〇〇の水やり」）に収まる長さにした
8. **登録・変更・アーカイブの後は、植物を読み直して返す**
   - マスタの和名（`speciesName`）と次回予定日を、一覧と同じクエリ（`GetPlant`）でそろえるため。クエリは2回になるが、操作の頻度は低い

## 残る課題
- 植物の変更の通知（`households.version` を増やす・リアルタイムの配信）は、タスク 11.x で加える
- 購入日が未来の日付でも受け付けている、「置き場所が未設定の植物」だけを絞り込む条件がない：リリース後に対応する（`docs/backlog.md`）
