# 0033. リマインダーは最後に使った端末のタイムゾーンで、時刻から1時間の間に1日1回送る

- 状態：採用
- 日付：2026-11-08
- 関連：タスク 12.3、`server/internal/job/reminders.go`、`server/internal/adapter/postgres/reminders.go`、`server/db/queries/reminders.sql`、`server/internal/domain/reminder.go`、要件15
- 前提：0031（ジョブの実行基盤）、0032（通知の文面・送信と記録を同じトランザクションで行う形）、設計の ReminderJob

## 決定
1. **ジョブ `reminders` を5分ごとに実行する。対象は、リマインダーが有効で、端末があるメンバー**（閲覧者を含む。要件15-8）
2. **時刻と日付は、メンバーが最後に使った端末（`last_seen_at` が最新）のタイムゾーンで判定する**（要件15-7）
   - 1日1回の記録（`reminder_dispatches`）はメンバーシップごとなので、メンバーのタイムゾーンを1つに決める必要がある。端末はアプリの起動のたびにタイムゾーンを更新するので、旅行先で開けば、その土地の時刻に切り替わる
   - 送り先は、そのユーザーのすべての端末
3. **送るのは、リマインダーの時刻から1時間の間（`domain.ReminderWindow`）だけ**
   - 設計の「時刻を過ぎていて、その日にまだ送っていない」だけだと、昼に参加したメンバーに朝のリマインダーが昼に届く、取り消しで夕方にタスクが戻ると急に届く、などが起きる
   - 1時間あれば、5分ごとの実行が何回か抜けても届く
   - 日付をまたぐ設定（23:30）は、0:10 でも「前の日」のリマインダーとして送る
   - 夏時間が始まる日にない時刻（ニューヨークの 2:30 など）は、Go の `time.Date` の決まりで、時計を進める前の時刻（1:30）から1時間とする
4. **送るかどうかは、端末の日付で「その日以前の未完了タスク」があるかで決める**（要件15-1・15-4）
   - 条件は今日やること一覧（9.1）と同じ（有効・削除していない・アーカイブしていない植物）。完了・スキップすると予定日が先に進むので、すべて済んだ日は0件になり、送らない
   - 送らなかった日は記録を作らない。1時間の間にタスクが戻れば（取り消しなど）、次の実行で送る
5. **1つのトランザクションで「タスクの確認 → 送信の記録 → 送信」を行い、1日1回をユニーク制約で保証する**（要件15-2）
   - 記録（`reminder_dispatches (membership_id, local_date)`）を `ON CONFLICT DO NOTHING` で作り、作れなければ（その日はもう送った）送らない。二重に実行しても、2回目は記録を作れない
   - 記録はメンバーシップから作るので、対象を選んだあとでリマインダーを切った・世帯を抜けたメンバーにも送らない
   - FCM に送れなければロールバックして記録を消し、1時間の間の次の実行で送り直す（1時間を過ぎたら諦める）
6. **文面**：タイトルは世帯名、本文は「今日のお手入れが4件あります（水やり3件、肥料1件）」。内訳の区切りは、完了通知（0032）とそろえて「、」にする（設計の例は「・」）。data は `type: reminder` と `householdId` で、タップするとその世帯の今日やること一覧を開く（要件15-5）
   - 世帯ごとに1件の通知にする（メンバーシップが世帯ごとなので、複数の世帯に所属していれば世帯の数だけ届く）

## 残る課題
- 対象の選び方は、リマインダーが有効なすべてのメンバーを読み、時刻の判定をジョブ（Go）で行う。家族の規模では軽いが、利用者が増えたら、時刻とタイムゾーンで絞り込む SQL とインデックスに変える（設計の「将来のボトルネック」）
- Cloud Scheduler のジョブ（5分ごと、`POST /internal/jobs/reminders`）の作成は、デプロイのタスクで行う
