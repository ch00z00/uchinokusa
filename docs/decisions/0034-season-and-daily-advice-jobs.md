# 0034. 季節の切り替えは、季節の初日を基準に1時間ごとに計算し直し、日次の助言は対象のプロバイダがいるときだけ植物を回る

- 状態：採用
- 日付：2026-11-08
- 関連：タスク 12.4、`server/internal/job/seasons.go`・`advice.go`、`server/internal/adapter/postgres/seasons.go`、`server/db/queries/seasons.sql`、`server/internal/domain/schedule.go`、要件8-7・19-5
- 前提：0018（周期を変えても次回予定は動かさない）、0021（手で変えた予定日の印）、0023（予定を決めた記録）、0027（助言プロバイダの仕組み）、0031（ジョブの実行基盤）

## 決定
1. **ジョブ `seasons` を1時間ごとに実行し、世帯のタイムゾーンで今日が季節の初日の世帯だけを計算し直す**（要件8-7）
   - 季節の初日は、北半球の 3/1・6/1・9/1・12/1（南半球は6か月ずらす。`domain.IsSeasonStart`）
   - 1日1回の実行だと、その1回が抜けたときに切り替えを取りこぼす。1時間ごとにすれば、初日のうちに何度か機会がある
2. **次回予定 = max(最後に完了した日 + 新しい季節の周期, 季節の初日)**（`Schedule.NextDueAtSeasonStart`）
   - 設計の式の「今日」を「季節の初日」にした。初日のうちに何度計算しても同じ結果になり、二重の実行でも変わらない
   - 初日に完了したタスクは、完了したときの計算（`NextDueAfterCompletion`）と同じ結果になるので、計算し直しても変わらない
   - 値が変わるタスクだけを更新し、変更イベント（task の updated）を出す。変わらなければ何もしない
3. **対象は、季節ごとの周期を持つ、有効なタスク**
   - 手で予定日を変えたタスク（`due_overridden`。スキップの確認日を含む）は除く（設計どおり）
   - 一時停止中・削除済みのタスクは除く。再開したときの次回予定は、再開の計算（0019）に任せる
   - 起点は、予定を決めた最新の記録（追加の記録を除く。0023 と同じ）。それが完了でない・記録がないタスク（一度も完了していない）は、ユーザーが決めた予定日のままにする
4. **完了と同じく、タスクの行をロックしてから計算し直す**
   - ロックと「最後の完了の読み出し」は別の文にする。PostgreSQL の `FOR UPDATE` は、ロックを待ったあと、ロックした行しか最新に読み直さない（ほかの表の行は、待つ前の値のまま）。1つの文にすると、待っている間に確定した完了を見落とし、古い完了から計算した値で上書きしてしまう
   - READ COMMITTED では文ごとに確定したデータを読むので、ロックを取ったあとの文なら、確定した完了が見える
5. **ジョブ `daily-advice` を1日1回実行し、毎日のきっかけ（`daily`）を持つプロバイダを、アーカイブしていない植物ごとに呼ぶ**（要件19-5）
   - MVP では対象のプロバイダがないので、植物を読まずに終わる。フェーズ2で天気と連動するプロバイダを `advisor.NewRegistry(...)` に登録すれば、このジョブがそのまま呼ぶ
   - 提案の保存・重複の防止は SuggestionService（0027）が行うので、二重に実行しても同じ提案は増えない
   - 処理件数は、評価した植物の数

## 残る課題
- 季節の切り替えで植え替えタスクの予定日が変わっても、避ける時期の助言（0028）は評価し直さない。backlog の「記録で予定日が変わっても評価し直さない」と同じ形で、困る声が出たら `task_due_changed` で評価する
- 季節の初日が丸1日分の実行で抜けたら、そのタスクは次の完了まで、前の季節の周期の予定日のままになる（次の完了からは新しい季節の周期になる）
- Cloud Scheduler のジョブ（`seasons` は1時間ごと、`daily-advice` は1日1回）の作成は、デプロイのタスクで行う
