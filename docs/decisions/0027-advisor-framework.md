# 0027. 助言プロバイダは提案を返すだけにし、保存・重複防止・採用・見送りは共通の仕組みで行う

- 状態：採用
- 日付：2026-11-06
- 関連：タスク 10.1、`server/internal/advisor/advisor.go`、`server/internal/domain/suggestion.go`、`server/internal/app/suggestion.go`、`server/internal/adapter/postgres/suggestions.go`、`server/db/migrations/00006_suggestion_task_schedule.sql`、要件19-1〜19-6・17-6
- 前提：設計の判断3（Advisor と suggestions テーブル）、0024

## 決定
1. **プロバイダ（`advisor.Advisor`）は、情報（`advisor.Context`）を受け取って提案（`advisor.Proposal`）を返すだけにする**（設計どおり）
   - 渡す情報は、きっかけ・世帯のタイムゾーンでの今日・対象のタスク（予定日の変更のとき）と、植物・世帯（地域・半球）・植物マスタ・置き場所・タスク（削除を除く）・最近の記録30件（スキップの理由を含む）（要件19-1）
   - 保存・重複の防止・一覧・採用・見送りは `app.SuggestionService` が共通で行う。新しいプロバイダは、`Advisor` を実装して `advisor.NewRegistry` に登録するだけで加えられる（要件19-5）
   - パッケージは設計どおり `internal/advisor` に分ける。プロバイダ（10.2 の植え替え、フェーズ2の天気）は、このパッケージに置く
   - プロバイダの ID が空・重複していれば、起動のときにエラーにする。提案元を見分けられなくなるため（要件19-6）
2. **プロバイダの失敗は、元の操作を失敗させない**（設計の「プロバイダの障害」）
   - `Evaluate` はエラーを返さず、ログに残すだけにする。植物の登録など、呼び出す側でエラーの扱いを考えなくてよいようにするため
   - プロバイダのエラー・panic は、そのプロバイダだけを飛ばす。エラーと一緒に返した提案も保存しない（途中までの結果かもしれないため）
   - 形の誤った提案（種類・行動の値が知らないもの、キーがない、`create_task` に作るタスクの種類・周期がない、条件つきに条件がない、有効期間が逆）は、その提案だけを保存しない。表示も採用もできない提案を残さないため
   - アーカイブした植物には、プロバイダを呼ばない
3. **重複の防止は、データベースのユニーク制約（`(household_id, dedupe_key)`）と `ON CONFLICT DO NOTHING` で行う**
   - 見送った提案も行を残すので、同じキーの提案は二度と作られない（要件17-6）。同時に評価しても、重複は保存されない
   - キーの形はプロバイダが決める（例：`repotting:initial:{plantID}`）。世帯の中で一意になるように、植物やタスクの ID を含める
4. **タスクを作る提案は、作るタスクの周期を持つ**（マイグレーション 00006）
   - 設計の `suggestions` テーブルには周期の列がなく、採用してもタスクを作れなかったため。列の形は `care_tasks` の周期にそろえる
   - 周期はプロバイダが決める。`create_task` の提案に、作業の種類と周期がなければ、データベースの CHECK 制約でも拒否する
5. **採用・見送りは、提案の行ロック（`FOR UPDATE`）の中で、未回答かを確かめてから記録する**
   - 同時の採用でタスクを二重に作らないため。後のほうは採用済みの提案を見て `409 already_responded` になる
   - 採用は、タスクの作成と同じトランザクションで行う。対応した人と日時を記録する（要件19-6）
   - 権限は `task.write`（編集者以上）。採用でタスクを作るため。見送りも同じ権限にする。一覧は閲覧者も見られる
6. **採用の規則は domain の純粋な関数（`PlanAcceptance`）にする**
   | 提案 | 結果 |
   |---|---|
   | 採用・見送り済み | `409 already_responded` |
   | 有効期間を過ぎた | `409 suggestion_expired` |
   | `create_task` | 提案日（`date` を送れば、その日）を予定日にしたタスクを作る（要件17-4・17-5） |
   | ほかの行動 | 採用したことを記録するだけ。`date` は送れない（`fields.date = invalid`） |
   - `skip_today` の提案を採用しても、サーバーはスキップを記録しない。スキップの理由と確認日はユーザーが選ぶので、アプリが記録の API（`POST /tasks/{id}/skips`）で行う
   - 見送りは、有効期間を過ぎた提案でもできる（表示から消すだけで、害がないため）
7. **一覧（`GET /households/{id}/suggestions?date=`）は、その日に有効な（未回答で、有効期間の中の）提案を、種類を問わず返す**。日付の決め方は、今日やること一覧と同じ（0024）
8. 有効期間を過ぎた提案は、状態を `expired` に変えず、有効期間で判定する。状態を変えるジョブを作らずに済むため。`expired` の値は、0028 で「撤回した提案」に使う

## 残る課題
- 植物の登録・植え替えタスクの予定日の変更から `Evaluate` を呼ぶのは、タスク 10.2 でつなぐ
- 日次のジョブ（`daily` のきっかけ）は、フェーズ2の天気連動のプロバイダとあわせて作る
- 提案の作成・採用・見送りを、ほかのメンバーの画面に配信する処理は、タスク 11.x で加える
