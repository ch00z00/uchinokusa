# 0035. アカウントの削除は1つのトランザクションで行い、取り消せない外部の処理（Apple・Firebase）はコミットの直前に行う

- 状態：採用
- 日付：2026-11-08
- 関連：タスク 13.1、`DELETE /v1/me`、`server/internal/app/account.go`、`server/internal/adapter/postgres/users.go`、`server/db/queries/account.sql`、`server/internal/adapter/apple/`、`server/internal/adapter/firebase/verifier.go`、要件1-6・1-7
- 前提：設計の AccountService と AppleRevoker、0029（変更イベント）

## 決定
1. **`DELETE /v1/me` で、1つのトランザクションの中で次の順に行う**
   1. 所属する世帯の行をロックし、ほかにメンバーのいる世帯の唯一のオーナーなら、何も消さずに `409 owner_transfer_required` と、オーナー権限を移すべき世帯（ID・名前）を返す（要件1-7）
   2. 自分だけがメンバーの世帯は、関連データごと消す（世帯の削除の変更イベント）。ほかの世帯からは外す（メンバーの削除の変更イベント）
   3. 記録・メモの作業者名を「退会したユーザー」（`domain.DeletedUserName`）にしてユーザーとのつながりを切り、まだ送っていない通知（自分が作業した完了通知・参加の通知）を取り消し、端末を消す
   4. ユーザーの行は、表示名を消し、削除済みの印（`deleted_at`）を付けて残す（下の7）
   5. コミットの直前に、Apple のトークンの失効（Apple でサインインしたユーザーだけ）と、Firebase Auth のユーザーの削除を行う
2. **確かめるのと消すのを同じトランザクションにし、世帯の行を最初にロックする**
   - 確かめてから消すまでの間に、招待から誰かが参加すると、ほかにメンバーのいる世帯を丸ごと消してしまう
   - メンバーシップの追加は、世帯の行を参照するロック（KEY SHARE）を取るので、世帯の行を `FOR UPDATE` でロックすれば、参加の途中ならそれが確定するまで待ち、確定したメンバーを数に入れられる
   - ほかの書き込みは世帯の行を最後にロックする（0029）ので、順序が食い違い、まれにデッドロックになる。PostgreSQL が片方を失敗させるので、やり直せば消せる。アカウントの削除はまれなので、受け入れる
3. **取り消せない外部の処理は、データベースの処理がすべて済んだあと、コミットの直前に行う**
   - 外部の処理に失敗したら、ロールバックして何も消さない。ユーザーはやり直せる
   - コミットのあとに行うと、外部の処理に失敗したときに、アカウントは消えたのに Apple のトークンが残る（やり直す手段がない）。Apple のトークンの失効は App Store の審査の要件なので、これを避ける
   - 外部の処理のあとでコミットに失敗した場合は、Apple・Firebase の連携が切れたアカウントが残る（ユーザーはサインインし直して、削除をやり直せる）。まれなので受け入れる
4. **Apple のトークンの失効は、Sign in with Apple の REST API で行う**
   - アプリは削除の直前に Apple で再認証し、認可コード（`appleAuthorizationCode`。有効期限5分、1回だけ使える）を送る。ないときは 422（`required`）
   - サーバーは、鍵（.p8）で署名したクライアントシークレット（ES256 の JWT、有効期限5分）で、認可コードからリフレッシュトークンを受け取り（`/auth/token`）、失効させる（`/auth/revoke`）。認可コードが無効なら 422（`invalid`。アプリは再認証し直す）
   - Apple の設定（`APPLE_TEAM_ID`・`APPLE_KEY_ID`・`APPLE_CLIENT_ID`・`APPLE_PRIVATE_KEY`）がなければ、Apple でサインインしたユーザーの削除は失敗にする（500）。黙って失効を飛ばすと、本番の設定漏れに気づけないため
   - JWT の署名には、Firebase Admin SDK が使っている `github.com/golang-jwt/jwt/v4` を直接の依存にして使う
5. **Firebase Auth のユーザーの削除は、すでに消えていても成功にする**（削除のやり直しで失敗しないように）
6. **作業者名の匿名化は、変更イベントを出さない**（記録・メモの件数だけイベントが出るのを避ける）。アプリは、メンバーの削除のイベントを受けたら、その世帯のデータを取り直す（`HANDOFF-mobile.md` への申し送り）
7. **ユーザーの行は消さずに、削除済みの印として残す**（1.3 のスキーマの `users.deleted_at` と、`GetOrCreate` の「削除済みなら見つからない」の考えどおり）
   - 行ごと消すと、ほかの端末に残っている ID トークン（最大1時間有効）で呼ばれたときに、初めてのユーザーとして作り直してしまい、トークンの名前（個人情報）がまた保存される
   - 印を残せば、古いトークンでのリクエストは 401 になる
   - 残すのは、Firebase の uid（Firebase のユーザーは消えているので、だれのものかはたどれない）と、作成・削除の日時だけ。表示名は消す

## 残る課題
- 招待の作成者（`invitations.created_by`）・提案の回答者（`suggestions.responded_by`）は、削除済みの印の行を指したまま残る（名前は消えているので、だれかはわからない）
